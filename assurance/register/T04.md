id: T04
title: Architecture-specific ABI qualification
status: partial
row: [PR100](https://github.com/riventic/air2lean/pull/100) merged with bounded alignment and three-version controls. [PR126](https://github.com/riventic/air2lean/pull/126): aarch64-linux-gnu and aarch64-macos-none are qualified separately: native probes run only on their own host (`scripts/aarch64-abi.py`: unusual integer widths, f16 to f128 and `c_longdouble` layouts and results, f80 invalid encodings, atomic cells including u24/u40 with padding, the widest atomic, the cache line, L09 vector images), Zig 0.16.0 expected results are versioned per profile, and Lean checks with kernel-checked layout tables are tied to each file; host exclusions never count as matches. [PR135](https://github.com/riventic/air2lean/pull/135): expected results for Zig 0.15.2 and 0.14.1 beside 0.16.0 on each aarch64 profile (aarch64-linux-gnu measured in a native `linux/arm64` container, aarch64-macos-none on Apple silicon), synchronization-boundary probes (every `@atomicRmw` operation on u8/i8, u24/i24, u40/i40, u64/i64 and u128/i128 cells, every ordering the compiler accepts for load, store, RMW and `cmpxchg`, bool, enum, pointer, f32 and f64 cells, three threaded litmus tests with deterministic outcomes) and twelve compile-reject limit programs; `Model.lean` checks each file and lists the declared divergences on both profiles (a signed `@atomicRmw` `Max` on a negative padded `i24`/`i40` cell keeps the negative cell; 0.14.1 and 0.15.2 soft-float `f80`/`f128` `@sqrt` is `f64`-precise only); CI runs the aarch64-linux job (`ubuntu-24.04-arm`) for the three versions and the macOS job for each. [PR143](https://github.com/riventic/air2lean/pull/143): aarch64-linux (gnu) AIR is translated, differentially tested and proof-built natively for 0.14.1–0.16.0 (the `aarch64-linux` job). [PR172](https://github.com/riventic/air2lean/pull/172): Zig 0.17.1 aarch64-linux is a declared translation path (`compatibility.json`, `assurance/target-matrix.json`): the `aarch64-linux` job builds the patched 0.17.1 natively, exports the examples' AIR on the host, compares it with the goldens (new `air-linux-aarch64/` overlays for `floatops` and `floatconv`), translates (`Gen-linux-aarch64.lean`), runs the differential test (0 mismatches, 86209 cases, recorded in a native `linux/arm64` container) and builds the proofs, as for 0.16.0/0.15.2/0.14.1; the padded-width `cmpxchg` and `.Max`/`.Min` rows are no longer declared divergences: `Model.lean` accepts a divergent row only when it is an operation the translator rejects (`PADDED_ATOMIC`, `rejectedByTranslator`; for an `atomic` row only its `cmpxchg` may differ), and a wider native probe (`u7`/`i7` to `u56`/`i56`, 0.14.1–0.17.1) shows every divergence is such an operation ([docs/aarch64-abi.md](docs/aarch64-abi.md)); weak ordering: nine litmus tests (MP, SB, LB, CoRR, WRC, IRIW with relaxed, release/acquire, acquire and `seq_cst` variants, 100 000 rounds each) observed natively on both profiles for 0.14.1–0.17.1 (`tests/roadmap/weak-ordering/observed/`, re-observed by the `aarch64-linux` and `macos` jobs), every observed outcome checked to be an outcome of the model's atomics by exhaustive exploration of `atomicLoadAt`/`atomicStoreAt` (`Litmus.lean`, forbidden outcomes checked at elaboration; observed: weak MP and IRIW on Apple silicon, SB on both; [docs/weak-ordering.md](docs/weak-ordering.md)); atomic `f80`: every atomic op (load and store at each ordering, each float RMW, `cmpxchg`) is built and run natively on both profiles for 0.14.1–0.17.1 (`atomic_f80.zig`, `f80atomic` rows): 0.14.1–0.16.0 fail to compile each one, and 0.17.1 compiles `@atomicStore` and stores the operand's address instead of its value ([upstream draft](docs/upstream/f80-atomic-store.md)); the translator rejects every float atomic, which `Model.lean` prints as rejected (never a match) and `tests/roadmap/aarch64-abi/test_float_atomics.py` checks on the CLI for `f16`–`f128` and every op on both profiles' AIR for the four versions ([docs/aarch64-abi.md](docs/aarch64-abi.md#atomic-f80)); futex: the kernel calls of the OS rows (`FUTEX_WAIT`/`FUTEX_WAKE`, private and shared, on aarch64-linux; `__ulock_wait2`/`__ulock_wait`/`__ulock_wake` on aarch64-macos) are observed natively on both profiles for 0.14.1–0.17.1 (`futex.zig`, 79 and 35 `futex` rows per expected file: return codes, the order of the timeout, alignment and address checks, wake limits including `val ≤ 0`, key domains, and a lock built on the two calls), and `tests/roadmap/aarch64-abi/Futex.lean` checks every row to be an outcome of `ZigLean/Os/Futex.lean` (premises OSF-01, OSF-02) over every schedule, failing on a missing, repeated, unknown or malformed row; thirteen calls at an address that is not a live word (null, unmapped, top-byte tagged, bit 63 alone) are refused by the model (`.illegal`, natively `-EFAULT`) and printed as refused, never as matches; no native row contradicts the rows ([docs/aarch64-abi.md](docs/aarch64-abi.md#futex)). [PR900](https://github.com/riventic/air2lean/pull/900): CPU-feature dependence: the probe also runs at three other CPUs on aarch64-linux (`generic+fullfp16`, `generic+lse+rcpc`, `generic+outline_atomics`) and four on aarch64-macos (`generic`, `generic+lse`, `apple_m1-fullfp16`, `apple_m1+outline_atomics`) for 0.14.1–0.17.1 (`cpu` rows: the rows that differ from the baseline, and the count that do not), and records `@mulAdd` on operands whose result depends on the format of the multiply-add (`fma` rows); the only result that depends on a CPU feature is an `f16` `@mulAdd` (`fullfp16`), and it also depends on the Zig version: natively, 0.17.1 without `fullfp16` computes it in `f64`, not in `f32` as 0.14.1–0.16.0, which the model had wrong on aarch64-linux and x86_64-linux (`@mulAdd(f16)` of bits `c290`, `c47c`, `0ffe`: native `4b5b`, model `4b5c`), as it had an aarch64-macos profile without `fullfp16` before 0.17.1; the translator's rule is now `Dialect.f16MulAdd` (the profile's `fullfp16`, Zig version, backend and target row), an aarch64 profile without `fp_armv8` is rejected, `Model.lean` checks every `fma` and `cpu` row against that rule and fails on any other CPU-dependent row, and `tests/roadmap/aarch64-abi/test_mul_add.py` checks the emitted term per target, version, feature, backend and float mode ([docs/aarch64-abi.md](docs/aarch64-abi.md#muladd-and-other-cpus)); with `outline_atomics`, 0.14.1 and 0.15.2 order a padded `u40`/`i40` `.Max`/`.Min` with the other signedness, an operation the translator rejects (printed as rejected, never a match). Remaining: instruction-level ordering strength is unprobed, and so are CPU feature sets other than the seven recorded; of the futex calls, `EINTR`, file-backed shared keys and `os_unfair_lock` are unprobed; build-mode records for 0.17.1 aarch64 ReleaseFast and ReleaseSmall (ReleaseSafe and Debug are recorded; see T06).
---
qualify aarch64-linux and aarch64-macos separately, including vector layout, unusual integer widths, f80/f128 behavior and synchronization boundaries. Acceptance: each profile has native probes, versioned expected results and proofs tied to that profile. Host exclusions cannot count as successful matches.
