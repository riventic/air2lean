parameterized size/resource bounds and arbitrary permitted failure decisions, including several failures in one run. Acceptance: resource-independent safety statements quantify over permitted outcomes; large valid engine fixtures do not fail solely because of the model's fixed cap.

Bounded progress ([PR124](https://github.com/riventic/air2lean/pull/124)): `Mem.allocPolicy` adds an arbitrary failure oracle over (attempt, bytes) and an optional live-heap budget; the default has no fixed cap (the differential harness selects its 1 MiB cap explicitly). [PR580](https://github.com/riventic/air2lean/pull/580): `appendEach_spec` (`Proofs/Lists/Policy.lean`) proves a translated ArrayList append client for every allocator that meets the allocator contract `CAllocSpec` and has room (`fits`) for each capacity the list grows to, so for every failure decision, with any number of failures in one run (partial correctness, as the contract). Native differential of the oracle and the budget ([allocation-policy.md](docs/allocation-policy.md#native-differential)): the lists differential (`scripts/diff.sh`) runs every allocating function natively and in the model under the same generated policy objects (oracle rules over attempt and bytes, live-byte budget; 200 cases, Zig 0.17.1, 0.16.0 and 0.15.2 on x86_64-linux, no mismatch), and the policy fixture compares twenty exact cases, with several failures in one run, and detects seven mutants.

Large valid fixtures (the second acceptance clause): the model's default policy has no cap, and the differential can select it (`"max_bytes": null` on both sides; a missing field keeps the harness's explicit 1 MiB cap). Six generated `sumRange` lines run under it: buffers of 1 MiB + 4 bytes (one item past the harness cap) up to 4 MiB, each written and read item by item, and one request whose byte count overflows (`OutOfMemory` before any request). Natively and in the model the large buffers are allocated and the sums agree (x86_64-linux, Zig 0.17.1, 0.16.0 and 0.15.2, no mismatch). These runs became practical with a fix of the executable model: `storeBytes` kept the checked block and set a modified copy into the memory, so every store copied the whole block and a loop of stores into one block was quadratic in its size (`sumRange(16000)` 3.7 s, a 1 MiB buffer about a quarter of an hour). Checked `@[csimp]` equalities now run the store in place ([kernel-eval-bytes.md](docs/kernel-eval-bytes.md#compiled-execution-stores-in-place-m03)); definitions, kernel reduction and proofs are unchanged. Only requests the host can hold are inputs: the model represents every allocated byte.

The model's line (`AllocTranslated/Large.lean`, over the 0.17.1 and the 0.16.0 translation, both targets) and the native runs' (stock Zig 0.17.1 and 0.16.0, `ReleaseSafe`, x86_64-linux and aarch64-macos) equal the line `page_large ok 1048577 4194304` of `expected-linux.txt` and `expected.txt`. Under the differential harness's policy, the old 1 MiB cap, the same run gives `page_large ok 0 0`, and `check.sh` requires that: the fixture fails with a cap in the default policy. Still on the `std` model: the six large `sumRange` lines, the 200 generated policy lines and the twenty cases of `tests/roadmap/allocation-policy` (step 5 of [allocator-model.md](docs/allocator-model.md#removing-the-hand-written-allocator-models-plan) moves them).
- **Runner depth for that fixture**: answered, no model change. The depth of `Zig.loop` grows with the iteration count only in Lean's interpreter (`#eval`, `lean --run`, so `fixtures.py run`): the loop's next round is a call through `CoN.bind`'s continuation, which the interpreter does not make as a tail call. Compiled, `sumsUnder {} [1048577, 4194304]` runs in 8 s and 1.5 GB, also in a 512 KiB stack. The fixture's lines therefore come from an executable (`alloc-translated-large`, `tests/roadmap/lakefile.toml`). It links the float library's archive, which a stock Zig builds, so `check.sh` runs it only with `AIR2LEAN_NATIVE_ZIG`, in check trees. Open: the model needs about 350 bytes of memory per byte of such a block (1.5 GB for 4 MiB), which bounds the sizes a fixture can use.
