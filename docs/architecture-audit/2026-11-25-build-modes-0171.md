# Build-mode audit 2026-11-25: the Zig 0.17.1 ReleaseFast/ReleaseSmall mismatches

Base: `origin/main` at `ff63dcb0e` (2026-11-25). The 0.17.1 build-mode runs of PR #824
([build-modes.md](../build-modes.md) §Native runs) compare native ReleaseFast and ReleaseSmall
binaries with the ReleaseSafe model and show two mismatches that the 0.16.0 runs do not show. This
report explains both. Severities as in [trust-chain.md](trust-chain.md).

| # | Severity | Finding | Status |
|---|---|---|---|
| BM-1 | **SOUNDNESS** | A bare `union` has a hidden safety tag only when runtime safety is on, so its layout (and `@sizeOf` of it and of every type that contains it) differs between ReleaseSafe and ReleaseFast/ReleaseSmall. The ReleaseFast/ReleaseSmall premise ("only removes safety checks, so it diverges only on executions with illegal behaviour") is false for such types: a no-throw proof can transfer a wrong value and miss illegal behaviour. Holds for 0.16.0 too; the 0.16.0 runs did not show it only because the differential oracle renders the 0.16.0 tag byte as a wildcard. | **open**: needs a premise/claim change (maintainer decision, §BM-1 Options) |
| BM-2 | model (group C) | Zig 0.17.1's f80 `@trunc` of a zero-extension pseudo-denormal returns the operand or the signed zero depending on how compiler_rt was optimized; the model picked the operand. | **fixed**: `.unspecified` (`Float.truncRt017Chk`), pinned `0-1` |
| BM-3 | HARDENING (test oracle) | `tests/diff/Diff.lean`'s `byteStr` renders a byte whose low 1–3 bits are defined (`.part m`, `m < 4`) as `??`, so the differential test never compares those bits. | open (§BM-3) |

## BM-1: bare-union layout depends on the build mode

### What the model computes

`examples/layout`'s `Num` is a bare union `union { int: u32, small: u8 }`. The ReleaseSafe AIR
gives it a hidden tag, so both translations store the tag at offset 4
(`tests/golden/0.17.1/layout/Gen.lean` and `Proofs/Layout/Gen.lean`, `setNum`, lines 1124 and
1129):

```lean
Zig.store (α := NumTag) 1 (p0.add 4) NumTag.small
```

The two translations differ only in `NumTag`'s `Zig.Enc` instance
(`Air2Lean/Air/Dialect.lean`'s `intPaddingExtended`):

| Version | `encode` | Tag byte of `NumTag.small` (1) | `byteStr` |
|---|---|---|---|
| 0.16.0 | `Zig.Enc.encode v.toBits` (`intEncOf`: value bits, padding undefined) | `.part 1 1` (bit 0 defined, bits 1–7 undefined) | `??` |
| 0.17.1 | `(Zig.intEncExt .little false 1).encode v.toBits` (zero-extended ABI integer, `FuncGen.store`) | `.int 1` | `01` |

Both encodings are right for ReleaseSafe: 0.17.1 stores the whole zero-extended byte, and native
ReleaseSafe of both versions writes `01` (input 1 of `tests/diff/layout/inputs/setNum.jsonl`:
`a0b02a43012a5f8a`). The tag store itself is unchanged since 0.14.1.

### Why 0.16.0 matched

The 0.16.0 model's line for input 1 renders the buffer as `a0b02a43??2a5f8a`; the wildcard digits
match any native byte, so the unchecked build's `00` compares equal. The 0.17.1 model renders
`a0b02a43012a5f8a`, and the unchecked build's `a0b02a43002a5f8a` differs. Native bytes are the same in
both versions (stock 0.16.0 and 0.17.1, every mode, measured on aarch64-macos):

| Mode | `@sizeOf(Num)` | buffer after `setNum(p, false, 1443871136)` |
|---|---|---|
| Debug, ReleaseSafe | 8 | `a0b02a43012a5f8a` |
| ReleaseFast, ReleaseSmall | 4 | `a0b02a43002a5f8a` |

So the 0.16.0 agreement was not a rule that excludes hidden-tag bytes: it is BM-3. Even in 0.16.0
the model's one defined bit (bit 0 = 1) disagrees with the unchecked build's `0`.

### Why this is a soundness finding

In ReleaseFast and ReleaseSmall the tag does not exist: `Num` is 4 bytes, and byte 4 is outside the
object. This is not illegal behaviour that the unchecked build stops checking; it is a different
type layout on a legal execution. The ReleaseFast record's claim (`assurance/build-modes.json`:
"a proof that a function never throws on given inputs implies its ReleaseFast build has no
illegal behaviour on those inputs and returns the modelled value") rests on the premise that
ReleaseFast "only removes safety checks, so it may diverge from the ReleaseSafe model only on
executions with illegal behaviour". The premise's exclusions (`@setRuntimeSafety(false)`,
`@setFloatMode(.optimized)`, CPU features, error tracing, comptime branches on
`@import("builtin").mode`) do not cover it. Counterexamples
([`bare-union-safety-tag.zig`](../../tests/roadmap/build-modes/reproducers/bare-union-safety-tag.zig),
stock 0.16.0 and 0.17.1):

1. **Wrong value.** `fn numSize() usize { return @sizeOf(Num); }`. Sema folds the constant from
   the ReleaseSafe layout, so the model returns 8 and never throws, and a theorem
   `numSize = pure 8` is provable. The ReleaseFast binary returns 4. The claim transfers 8.
2. **Missed illegal behaviour.** `numBytes(buf)` returns `buf[0..@sizeOf(Num)]`: length 8 in the
   model, 4 in the unchecked build. A caller that indexes the slice with `i & 7` never throws in
   the model, so a no-throw proof follows; in ReleaseFast every `i & 7` in 4..7 is an
   out-of-bounds index, illegal behaviour with no check. This is the core transfer claim of
   README.md ("a proof that a function never throws in this model also shows that its
   `ReleaseFast` build has no illegal behaviour on those inputs"), and it is false here.
3. **Wrong memory.** After `setNum(p, false, v)` the model's byte `p + 4` is `1` (0.17.1: a whole
   byte; 0.16.0: bit 0), and a theorem about it is provable; the unchecked build leaves the
   byte unchanged. This is the 171-case mismatch.

The claim scope does not exclude these: the profile's `build_mode` is `ReleaseSafe` by design (the
whole point of the transfer is to reach the other modes from it), and no exclusion names layout.
The finding applies to the 0.16.0 qualification records too; the 0.16.0 runs hide only the third
counterexample, and only by BM-3.

### Options

The fix is not a harness rule for `setNum`'s byte: a wildcard or pin for hidden-tag bytes would
hide counterexample 3 and leave 1 and 2 untouched.

- **A (recommended): name the safety-dependent layouts in the premise and fail closed on them.**
  The premise and the ReleaseFast/ReleaseSmall claim exclude every type whose layout depends on
  runtime safety: a bare union with a safety tag and every type that contains one, and every
  comptime value derived from their layout (`@sizeOf`, `@offsetOf`, `@bitOffsetOf`, a length or
  index computed from them). The translator already knows these types (it emits the hidden tag
  type, e.g. `NumTag`); it records them in the generated header (as it records the
  `float_mode` and admissions), and the claim tooling refuses the ReleaseFast/ReleaseSmall transfer
  for a function whose translation touches one (fail closed). The diff runs then classify such a
  function's unchecked-mode cases by that header fact, one mechanism for every bare union and
  every version, and the record cites the exception with the reproducer, as float `@divExact`
  did. Cost: a premise text and claim-scope change (`assurance/build-modes.json`, README sentence,
  `docs/build-modes.md`), a header field, a claims-tool check.
- **B: translate the unchecked layout.** Export ReleaseFast AIR for functions with
  safety-dependent layouts and prove them against that model. Rejected: the design translates
  only the ReleaseSafe profile, and two models of one function is the second framework that
  CLAUDE.md forbids.
- **C: exclude whole modules that declare a bare union.** A coarser A: simpler to check, but it
  drops the transfer for every function of such a module.
- **D: hidden-tag bytes as undefined in the model.** Rejected: ReleaseSafe writes a defined tag
  and reads it for the safety check (`numInt` panics on the inactive field), so the model would
  lose that, and `@sizeOf` stays 8.

A, B and C change a premise or a claim, so they are the maintainer's decision. Until then there is
no 0.17.1 ReleaseFast/ReleaseSmall record: `scripts/build-modes.py check` needs every mismatch of a
qualified record under one of its exceptions, and `layout.setNum` is under none.

## BM-2: f80 `@trunc` of a zero-extension pseudo-denormal

Rows 3647 and 3741 of `tests/diff/floatops/inputs/op80.jsonl` take `@trunc` (selector 12) of
`0x0000_8000000000000000`, a pseudo-denormal whose low 63 fraction bits are zero. Zig 0.17.1's
`trunc_f80` is `@floatCast(trunc_f128(x))`. `__extendxftf2` drops the explicit integer bit, so the
f128 extension is `+0`; `trunc_f128(+0)` takes its `u & m == 0` path and returns its argument, and
then the result depends on whether LLVM 22 folds `fptrunc (fpext x)` back to `x` where it
compiles this code (a folding `truncl` reloads the saved operand). Whether it does varies with
the build mode and the target. Stock 0.17.1
(`@trunc` of `±0x0000_8000000000000000`):

| Target | Debug | ReleaseSafe | ReleaseFast | ReleaseSmall |
|---|---|---|---|---|
| x86_64-linux (diff runs, PR #824) | operand | operand | operand | `+0` |
| x86_64-macos (Rosetta, this audit) | operand | operand | `±0` | `±0` |
| aarch64-macos (soft f80, this audit) | `±0` | `±0` | `±0` | `±0` |
| 0.16.0, every target above | `±0` | `±0` | `±0` | `±0` |

The model (`Float.truncRt017Chk`, compiler-rt mode, 0.17.1) returned the operand. This is the same
class as the pseudo-encoding family of group C: Zig defines no value for a non-canonical f80
encoding, and compiler_rt's result on it is not one value. The family rule missed it because
`trunc_f80`'s other paths are deterministic: for every other operand `fptrunc (fpext x)` is `x`
or `trunc_f128` returns new bits (no fold), and `round_f80`, the other routine with this shape,
returns `0 * x` on these operands, never `x`. `fma_f80` already excludes pseudo-denormals, and the
transcendental routines are opaque. So the zero-extension pseudo-denormal of `@trunc` is the
whole fold-dependent set, and `.unspecified` there completes the rule.

**Fix.** `Float.truncRt017Chk` throws `.unspecified` on `Float.isZeroExtPseudoDenormalF80`
(`ZigLean/Float/CompilerRt.lean`); `Float.truncRt017Chk_eq` and the proofs that use it
(`Proofs/Floatops/Proofs.lean`: `op80_spec`, `softF80Chk_truncRt017`) assume no pseudo-denormal and
are unchanged. The two inputs are pinned `0-1` in `tests/diff/floatops/unspecified.txt` (1 on
0.17.1, 0 on 0.16.0, whose model gives `+0`, as every 0.16.0 build does). The aarch64 pin files
already exclude them (soft f80). IEEE mode still returns the mathematical truncation `±0`
(docs/floats.md group I). 0.16.0 keeps `Float.truncChk`: its LLVM does not fold in any mode
measured.

**Upstream.** Not drafted: this is not a miscompilation. Zig defines no value for the encoding,
and the fold is valid for every canonical value.

## BM-3: the oracle hides defined low bits

`byteStr` (`tests/diff/Diff.lean`) prints `.part m x` as `?` plus the low hex digit when `m ≥ 4`,
and as `??` when `m < 4`; `.mask d x` prints a digit only where all four of its bits are
defined. A model byte with 1 to 3 defined bits is therefore compared as a full wildcard: in 0.16.0
every store of an integer whose width is 1 to 3 above a multiple of 8 (enum tags such as `NumTag`) is untested
in its defined bits. That hid BM-1's third counterexample. Fix direction: a rendering with
per-bit wildcards, and `scripts/diff-report.py`'s comparison taught it; it would show the 0.16.0
`setNum` disagreement in the unchecked modes as well. Not done here: it changes the oracle's wire
format and is independent of the two mismatches.
