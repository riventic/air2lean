# Build-mode audit 2026-11-25: the Zig 0.17.1 ReleaseFast/ReleaseSmall mismatches

Base: `origin/main` at `ff63dcb0e` (2026-11-25). The 0.17.1 build-mode runs of PR #824
([build-modes.md](../build-modes.md) §Native runs) compare native ReleaseFast and ReleaseSmall
binaries with the ReleaseSafe model and show two mismatches that the 0.16.0 runs do not show. This
report explains both. Severities as in [trust-chain.md](trust-chain.md).

| # | Severity | Finding | Status |
|---|---|---|---|
| BM-1 | **SOUNDNESS** | A bare `union` has a hidden safety tag only when runtime safety is on, so its layout (and `@sizeOf` of it and of every type that contains it) differs between ReleaseSafe and ReleaseFast/ReleaseSmall. The ReleaseFast/ReleaseSmall premise ("only removes safety checks, so it diverges only on executions with illegal behaviour") is false for such types: a no-throw proof can transfer a wrong value and miss illegal behaviour. Holds for 0.16.0 too; the 0.16.0 runs did not show it only because the differential oracle renders the 0.16.0 tag byte as a wildcard. | **open**: maintainer chose option A (2026-11-25); its mechanism is held by BM-4 |
| BM-2 | model (group C) | Zig 0.17.1's f80 `@trunc` of a zero-extension pseudo-denormal returns the operand or the signed zero depending on how compiler_rt was optimized; the model picked the operand. | **fixed**: `.unspecified` (`Float.truncRt017Chk`), pinned `0-1` |
| BM-4 | **SOUNDNESS** | BM-1 is wider than bare unions. `std.debug.SafetyLock` is 0 bytes without runtime safety, so `std.AutoHashMapUnmanaged`, `std.AutoArrayHashMapUnmanaged` (every version) and `std.ArrayList` (0.17.x) are 8 bytes smaller in ReleaseFast/ReleaseSmall; `std.heap.DebugAllocator`, `StackFallbackAllocator` and every user type chosen by a comptime branch on the mode differ too. The safe AIR shows none of these as mode-dependent. | **open**: option A as decided cannot detect them from the AIR (§BM-4); mechanism is a maintainer decision |
| BM-3 | HARDENING (test oracle) | `tests/diff/Diff.lean`'s `byteStr` renders a byte whose low 1–3 bits are defined (`.part m`, `m < 4`) as `??`, so the differential test never compares those bits. | **fixed** (§BM-3): per-bit rendering and comparison; it now shows BM-1's counterexample 3 in the 0.16.0 ReleaseFast/ReleaseSmall runs (155 of 300 `layout.setNum` cases) |

## BM-1: bare-union layout depends on the build mode

### What the model computes

`examples/layout`'s `Num` is a bare union `union { int: u32, small: u8 }`. The ReleaseSafe AIR
gives it a hidden tag, so both translations store the tag at offset 4
(`tests/golden/0.17.1/layout/Gen.lean` and `Proofs/Layout/Gen.lean`, `setNum`, lines 1124 and
1129):

```lean
Zig.store (α := NumTag) 1 (p0.add 4) NumTag.small
```

The two translations differ only in `NumTag`'s `Zig.Enc` instance
(`Air2Lean/Air/Dialect.lean`'s `intPaddingExtended`):

| Version | `encode` | Tag byte of `NumTag.small` (1) | `byteStr` |
|---|---|---|---|
| 0.16.0 | `Zig.Enc.encode v.toBits` (`intEncOf`: value bits, padding undefined) | `.part 1 1` (bit 0 defined, bits 1–7 undefined) | `??` |
| 0.17.1 | `(Zig.intEncExt .little false 1).encode v.toBits` (zero-extended ABI integer, `FuncGen.store`) | `.int 1` | `01` |

Both encodings are right for ReleaseSafe: 0.17.1 stores the whole zero-extended byte, and native
ReleaseSafe of both versions writes `01` (input 1 of `tests/diff/layout/inputs/setNum.jsonl`:
`a0b02a43012a5f8a`). The tag store itself is unchanged since 0.14.1.

### Why 0.16.0 matched

The 0.16.0 model's line for input 1 renders the buffer as `a0b02a43??2a5f8a`; the wildcard digits
match any native byte, so the unchecked build's `00` compares equal. The 0.17.1 model renders
`a0b02a43012a5f8a`, and the unchecked build's `a0b02a43002a5f8a` differs. Native bytes are the same in
both versions (stock 0.16.0 and 0.17.1, every mode, measured on aarch64-macos):

| Mode | `@sizeOf(Num)` | buffer after `setNum(p, false, 1443871136)` |
|---|---|---|
| Debug, ReleaseSafe | 8 | `a0b02a43012a5f8a` |
| ReleaseFast, ReleaseSmall | 4 | `a0b02a43002a5f8a` |

So the 0.16.0 agreement was not a rule that excludes hidden-tag bytes: it is BM-3. Even in 0.16.0
the model's one defined bit (bit 0 = 1) disagrees with the unchecked build's `0`.

### Why this is a soundness finding

In ReleaseFast and ReleaseSmall the tag does not exist: `Num` is 4 bytes, and byte 4 is outside the
object. This is not illegal behaviour that the unchecked build stops checking; it is a different
type layout on a legal execution. The ReleaseFast record's claim (`assurance/build-modes.json`:
"a proof that a function never throws on given inputs implies its ReleaseFast build has no
illegal behaviour on those inputs and returns the modelled value") rests on the premise that
ReleaseFast "only removes safety checks, so it may diverge from the ReleaseSafe model only on
executions with illegal behaviour". The premise's exclusions (`@setRuntimeSafety(false)`,
`@setFloatMode(.optimized)`, CPU features, error tracing, comptime branches on
`@import("builtin").mode`) do not cover it. Counterexamples
([`bare-union-safety-tag.zig`](../../tests/roadmap/build-modes/reproducers/bare-union-safety-tag.zig),
stock 0.16.0 and 0.17.1):

1. **Wrong value.** `fn numSize() usize { return @sizeOf(Num); }`. Sema folds the constant from
   the ReleaseSafe layout, so the model returns 8 and never throws, and a theorem
   `numSize = pure 8` is provable. The ReleaseFast binary returns 4. The claim transfers 8.
2. **Missed illegal behaviour.** `numBytes(buf)` returns `buf[0..@sizeOf(Num)]`: length 8 in the
   model, 4 in the unchecked build. A caller that indexes the slice with `i & 7` never throws in
   the model, so a no-throw proof follows; in ReleaseFast every `i & 7` in 4..7 is an
   out-of-bounds index, illegal behaviour with no check. This is the core transfer claim of
   README.md ("a proof that a function never throws in this model also shows that its
   `ReleaseFast` build has no illegal behaviour on those inputs"), and it is false here.
3. **Wrong memory.** After `setNum(p, false, v)` the model's byte `p + 4` is `1` (0.17.1: a whole
   byte; 0.16.0: bit 0), and a theorem about it is provable; the unchecked build leaves the
   byte unchanged. This is the 171-case mismatch.

The claim scope does not exclude these: the profile's `build_mode` is `ReleaseSafe` by design (the
whole point of the transfer is to reach the other modes from it), and no exclusion names layout.
The finding applies to the 0.16.0 qualification records too; the 0.16.0 runs hide only the third
counterexample, and only by BM-3.

### Options

The fix is not a harness rule for `setNum`'s byte: a wildcard or pin for hidden-tag bytes would
hide counterexample 3 and leave 1 and 2 untouched.

- **A (recommended): name the safety-dependent layouts in the premise and fail closed on them.**
  The premise and the ReleaseFast/ReleaseSmall claim exclude every type whose layout depends on
  runtime safety: a bare union with a safety tag and every type that contains one, and every
  comptime value derived from their layout (`@sizeOf`, `@offsetOf`, `@bitOffsetOf`, a length or
  index computed from them). The translator already knows these types (it emits the hidden tag
  type, e.g. `NumTag`); it records them in the generated header (as it records the
  `float_mode` and admissions), and the claim tooling refuses the ReleaseFast/ReleaseSmall transfer
  for a function whose translation touches one (fail closed). The diff runs then classify such a
  function's unchecked-mode cases by that header fact, one mechanism for every bare union and
  every version, and the record cites the exception with the reproducer, as float `@divExact`
  did. Cost: a premise text and claim-scope change (`assurance/build-modes.json`, README sentence,
  `docs/build-modes.md`), a header field, a claims-tool check.
- **B: translate the unchecked layout.** Export ReleaseFast AIR for functions with
  safety-dependent layouts and prove them against that model. Rejected: the design translates
  only the ReleaseSafe profile, and two models of one function is the second framework that
  CLAUDE.md forbids.
- **C: exclude whole modules that declare a bare union.** A coarser A: simpler to check, but it
  drops the transfer for every function of such a module.
- **D: hidden-tag bytes as undefined in the model.** Rejected: ReleaseSafe writes a defined tag
  and reads it for the safety check (`numInt` panics on the inactive field), so the model would
  lose that, and `@sizeOf` stays 8.

A, B and C change a premise or a claim, so they are the maintainer's decision. Until then there is
no 0.17.1 ReleaseFast/ReleaseSmall record: `scripts/build-modes.py check` needs every mismatch of a
qualified record under one of its exceptions, and `layout.setNum` is under none.

## BM-4: classification of mode-dependent layouts

The maintainer chose option A for BM-1 (2026-11-25), on the condition that a general classification
of every construct whose layout differs between safe and unchecked modes comes first. This is that
classification. It shows that option A, as specified (the translator records the types that the
safe AIR marks), cannot find most of them, so the mechanism was not built.

### Compiler (Sema), 0.14.1–0.17.1

In all five supported compilers the only place where a type's layout reads the optimize mode is
the tag decision for a union without an explicit tag: `runtime_tag`/`tag_usage` is `.safety` when
`Block.wantSafeTypes()` holds, i.e. `want_safety` (`@setRuntimeSafety` of the enclosing scope)
or else the owner module's mode is Debug or ReleaseSafe (0.14.1 `Sema.zig` 507, 3308, 22299; 0.15.2
528, 3376, 21153; 0.16.0 537, 20566, 34658; 0.17.0 539, 20615, 35430; 0.17.1 539, 20684, 35544:
`wantSafeTypes`, `zirReify`/`zirReifyUnion`, `zirUnionDecl`). That covers both declared
unions and reified ones (`@Type` up to 0.15.2, `@Union` from 0.16.0). There is no other
`optimize_mode` read in `Sema.zig`, `Type.zig`, `InternPool.zig`, `Value.zig` or `Zcu/`. The AIR
export records the result as the union type's `safety_tag` field, so the translator can classify
these exactly. A union declared in a scope with `@setRuntimeSafety(true)` keeps its tag in every
mode, and one declared under `@setRuntimeSafety(false)` has none in any mode. Classifying every
`safety_tag` union as mode-dependent over-approximates only the first case.

Error unions, `anyerror`, optionals, slices, extern, packed and tagged unions do not depend on
the mode. Error-return tracing changes function ABI and `@errorReturnTrace`, not data layout,
and the premise already excludes it.

### Language: comptime branches on the mode

`@import("builtin").mode` and `std.debug.runtime_safety` (derived from it) are comptime values.
Sema resolves a branch on them once, for the build being compiled, so the safe AIR contains only
the taken branch and has no marker that a branch existed. A type, a constant or a function body
selected this way is a layout or behaviour difference by definition, and the translator cannot see
it. The premise already excludes "comptime branches on `@import("builtin").mode`" in its text, but
nothing checks it, and std uses such branches internally.

### std types (measured)

[`safety-layout-probe.zig`](../../tests/roadmap/build-modes/reproducers/safety-layout-probe.zig)
and the reified-union probes
([`@Type`](../../tests/roadmap/build-modes/reproducers/safety-layout-reify-type.zig),
[`@Union`](../../tests/roadmap/build-modes/reproducers/safety-layout-reify-union.zig)) print
`@sizeOf`, `@alignOf` and a following field's `@offsetOf` for each candidate. They were built with each
stock compiler (0.14.1, 0.15.2, 0.16.0, 0.17.1; 0.17.0 was not run; its `SafetyLock`, `ArrayList`
and hash-map declarations are 0.17.1's) for `aarch64-linux-musl` and run in a native `linux/arm64` container. Rows that differ
between modes (D = Debug, RS = ReleaseSafe, RF = ReleaseFast, Sm = ReleaseSmall; sizes in bytes):

| Construct | Versions | D | RS | RF | Sm | Cause |
|---|---|---|---|---|---|---|
| bare `union { u32, u8 }` (declared or reified) | all | 8 | 8 | 4 | 4 | safety tag (Sema) |
| struct containing it, `@offsetOf` of the next field | all | 8 | 8 | 4 | 4 | safety tag |
| `if (std.debug.runtime_safety) u64 else u32` | all | 8 | 8 | 4 | 4 | comptime branch |
| `std.debug.SafetyLock` | 0.14.1–0.16.0 | 1 | 1 | 0 | 0 | comptime branch (`State`) |

| `std.AutoArrayHashMapUnmanaged` / `array_hash_map.Auto` | all | 40 | 40 | 32 | 32 | same |

The same in every mode: optionals, slices, `anyerror`, error unions, tagged/extern/packed unions,
`std.ArrayList` before 0.17, `MultiArrayList`, `ArenaAllocator`, `FixedBufferAllocator`,
`MemoryPool`, `Random.DefaultPrng`, `std.Thread.{Condition,RwLock,WaitGroup,ResetEvent,Semaphore}`
(0.14.1/0.15.2), `std.Io.{Mutex,Condition,RwLock,Semaphore,Group,Threaded}` (0.16.0, 0.17.1).
The Debug-only rows do not affect the transfer claim: Debug is qualified only for agreement on
the tested inputs.

Behaviour branches without a layout difference that reach translated programs include
`start.zig` (`use_safe_allocator`: `init.gpa` is the safe allocator in Debug/ReleaseSafe and
`smp_allocator`/`c_allocator` otherwise), `std.log.default_level` (ReleaseSmall), `std.fmt.digits2`
(ReleaseSmall) and the `SafetyLock` methods. As with the layout rows, the safe AIR shows only the
safe branch.

The committed 0.17.1 translations already contain such a type: `examples/lists` uses
`array_list.Aligned(u32,null)`, whose `debug.SafetyLock` field is in the golden AIR
(`tests/golden/0.17.1/lists/air/`). The 0.17.1 unchecked-mode runs show no `lists` mismatch only
because the harness does not observe the list header's bytes. BM-1's counterexamples 1 and 2
(`@sizeOf` folded to the safe value, a slice whose length is that size) apply unchanged to
`std.ArrayList(T)` in 0.17 and to the hash maps in every version.

### Why option A is insufficient as specified

Option A has the translator record the types that the safe AIR marks as mode-dependent. Only
the safety tag is marked (`safety_tag`). Every other row comes from a comptime branch, and the
safe AIR gives no way to tell it apart from a mode-independent type: `debug.SafetyLock.State` is
a plain non-exhaustive `enum(usize)`. Recording only `safety_tag` types and refusing only those
would leave the transfer open for every program that uses a hash map (all versions) or an
`ArrayList` (0.17), so it would not fail closed. A list of std type names in the translator would
be a per-case allow-list (CLAUDE.md "one mechanism"), and it would still miss user code that
branches on the mode.

### Options for the mechanism (maintainer decision)

- **M1: layout export of the unchecked modes.** The patched exporter also analyzes the program
  with `-OReleaseFast` and `-OReleaseSmall` (`-fno-emit-bin`, no AIR bodies) and writes their type
  tables. The translator compares each type reachable from the translated functions by fully
  qualified name (size, alignment, field offsets and types). It records every type that differs,
  or that is missing on one side (fail closed), in the header, and the claim tooling refuses the
  transfer for that mode. This is general for layout: it covers the safety tag, `SafetyLock`, user
  branches and the ReleaseSmall-only `Ghash`. It does not cover behaviour branches (same layout,
  different code), so the premise would keep excluding those by text alone.
- **M2: the exporter records reads of the mode.** The patched Sema marks an analysis unit (a
  function body, or a type's layout resolution) when it reads `builtin.mode` or
  `wantSafeTypes`. `std.debug.runtime_safety` derives from `builtin.mode`, so reading it propagates
  the mark through the incremental-compilation dependency graph. The export records the mark per
  function and per type, and the translator writes the marked
  types and functions reachable from the program into the header. This covers layout and
  behaviour alike. It over-approximates: a branch whose safe and unchecked arms agree, such as
  `log.default_level` for ReleaseFast, is still marked. `std.debug.assert` does not read the mode
  (0.14.1–0.17.1), so a program stays unmarked unless it reaches a declaration that does. It is the larger patch, needed in all five
  compiler versions.
- **M3: the coarse rule.** Drop the ReleaseFast/ReleaseSmall transfer for any program whose
  export reaches `std.debug.SafetyLock`, `DebugAllocator` or a mode branch. This is M2 without
  precision and still needs M2's detection for user branches. Rejected.

Recommendation: M2. It enforces exactly the exclusion that the premise already states ("comptime
branches on the mode") together with the safety tag, from the lowest-level fact (Sema's read of the
mode), and nothing is per type. M1 is the fallback if the dependency-tracking patch proves too
invasive for the older compilers. Either way, the claim-tooling check, the header field, the
`layout_excluded` differential rule and the tests from the maintainer's decision stay as
specified. Only the source of the classification changes, from the AIR's `safety_tag` to the
exporter's record.

## BM-2: f80 `@trunc` of a zero-extension pseudo-denormal

Rows 3647 and 3741 of `tests/diff/floatops/inputs/op80.jsonl` take `@trunc` (selector 12) of
`0x0000_8000000000000000`, a pseudo-denormal whose low 63 fraction bits are zero. Zig 0.17.1's
`trunc_f80` is `@floatCast(trunc_f128(x))`. `__extendxftf2` drops the explicit integer bit, so the
f128 extension is `+0`; `trunc_f128(+0)` takes its `u & m == 0` path and returns its argument, and
then the result depends on whether LLVM 22 folds `fptrunc (fpext x)` back to `x` where it
compiles this code (a folding `truncl` reloads the saved operand). Whether it does varies with
the build mode and the target. Stock 0.17.1
(`@trunc` of `±0x0000_8000000000000000`):

| Target | Debug | ReleaseSafe | ReleaseFast | ReleaseSmall |
|---|---|---|---|---|
| x86_64-linux (diff runs, PR #824) | operand | operand | operand | `+0` |
| x86_64-macos (Rosetta, this audit) | operand | operand | `±0` | `±0` |
| aarch64-macos (soft f80, this audit) | `±0` | `±0` | `±0` | `±0` |
| 0.16.0, every target above | `±0` | `±0` | `±0` | `±0` |

The model (`Float.truncRt017Chk`, compiler-rt mode, 0.17.1) returned the operand. This is the same
class as the pseudo-encoding family of group C: Zig defines no value for a non-canonical f80
encoding, and compiler_rt's result on it is not one value. The family rule missed it because
`trunc_f80`'s other paths are deterministic: for every other operand `fptrunc (fpext x)` is `x`
or `trunc_f128` returns new bits (no fold), and `round_f80`, the other routine with this shape,
returns `0 * x` on these operands, never `x`. `fma_f80` already excludes pseudo-denormals, and the
transcendental routines are opaque. So the zero-extension pseudo-denormal of `@trunc` is the
whole fold-dependent set, and `.unspecified` there completes the rule.

**Fix.** `Float.truncRt017Chk` throws `.unspecified` on `Float.isZeroExtPseudoDenormalF80`
(`ZigLean/Float/CompilerRt.lean`); `Float.truncRt017Chk_eq` and the proofs that use it
(`Proofs/Floatops/Proofs.lean`: `op80_spec`, `softF80Chk_truncRt017`) assume no pseudo-denormal and
are unchanged. The two inputs are pinned `0-1` in `tests/diff/floatops/unspecified.txt` (1 on
0.17.1, 0 on 0.16.0, whose model gives `+0`, as every 0.16.0 build does). The aarch64 pin files
already exclude them (soft f80). IEEE mode still returns the mathematical truncation `±0`
(docs/floats.md group I). 0.16.0 keeps `Float.truncChk`: its LLVM does not fold in any mode
measured.

**Upstream.** Not drafted: this is not a miscompilation. Zig defines no value for the encoding,
and the fold is valid for every canonical value.

## BM-3: the oracle hides defined low bits

`byteStr` (`tests/diff/Diff.lean`) prints `.part m x` as `?` plus the low hex digit when `m ≥ 4`,
and as `??` when `m < 4`; `.mask d x` prints a digit only where all four of its bits are
defined. A model byte with 1 to 3 defined bits is therefore compared as a full wildcard: in 0.16.0
every store of an integer whose width is 1 to 3 above a multiple of 8 (enum tags such as `NumTag`) is untested
in its defined bits. That hid BM-1's third counterexample. Fix direction: a rendering with
per-bit wildcards, and `scripts/diff-report.py`'s comparison taught it; it would show the 0.16.0
`setNum` disagreement in the unchecked modes as well. Not done here: it changes the oracle's wire
format and is independent of the two mismatches.

The gap was wider than 1 to 3 bits: `.part m x` with `m` = 5, 6 or 7 printed only the low digit,
so bits 4 to `m - 1` (the high bits of a `u5`…`u7` byte) were not compared either, nor were the
defined bits of a `.mask` digit that is only partly defined (a packed field next to undefined
bits).

**Fixed (2026-11-25, lane bm3-oracle).** One mechanism for every byte: `byteStr` renders a byte
from its defined-bit mask `d` and values `x` (`Zig.Byte.defBits`), a hex digit where all four bits
of the digit are defined, `?` where none is, and `(<d>:<x>)` for a byte with a partly defined
digit (`.part 1 1` = `(01:01)`); `scripts/diff-report.py`'s `buffer_match` matches a native byte
`z` iff `z & d = x` and rejects any other token (docs/generated-code.md §Differential test).
Regressions: `#guard`s on `byteStr` in `tests/diff/Diff.lean` (the `.part 1 1` guard fails on the
old renderer, which gave `??`) and `tests/roadmap/outcome-accounting/test_report.py` (a seeded
native byte whose defined bit 0 disagrees with `(01:01)` is a `mismatch` through the classifier,
the agreeing one a `value_match`; the old rendering `??` matched it).

Re-run (x86_64-linux, native, stock Zig, LLVM; `layout`, `lists`, `pointers`, `slices`, the
examples whose buffers the change can affect; 0.17.1 through `check-tree.py --host-goldens`), same
runs on `main` and on the branch:

| Version | ReleaseSafe | ReleaseFast | ReleaseSmall |
|---|---|---|---|
| 0.16.0 | 0 mismatches (unchanged) | **155** `layout.setNum` (was 0) | **155** `layout.setNum` (was 0) |
| 0.17.1 | 0 (unchanged) | 171 `layout.setNum` (unchanged, BM-1) | 171 `layout.setNum` (unchanged, BM-1) |

The new mismatches are BM-1's counterexample 3 in 0.16.0, now visible: input 1 of
`tests/diff/layout/inputs/setNum.jsonl` (`setNum(p, false, 1443871136)`): native
`a0b02a43002a5f8a`, model `a0b02a43(01:01)2a5f8a` (the model's tag bit 0 is 1, the unchecked
build leaves the input byte `00`). 155 rather than 171 cases: only bit 0 is defined in 0.16.0, so
the 16 inputs whose untouched byte 4 already has the tag's bit 0 still match. No other function
changed outcome. Consequence: the committed 0.16.0 ReleaseFast and ReleaseSmall records
(`assurance/build-mode-runs/0.16.0--*--Release{Fast,Small}--llvm.json`, 0 mismatches) no longer
reproduce: `build-modes.py record --verify` of those runs fails until BM-1 is decided. They are
left as they are (no build-mode record changes while BM-1/BM-4 are open); they claim what BM-1
shows to be false.

The Debug runs of this re-run used Zig's default Debug backend on x86_64-linux (stage2_x86_64)
against the LLVM-profile translation and showed `layout.nibArg` (8) and, in 0.16.0,
`layout.setNib` (165) on `main` and on the branch alike: the documented signed packed-union field
miscompilation of that backend (docs/build-modes.md, 173 cases; `layout` is rejected under the
stage2_x86_64 profile). Not a BM-3 effect. Not re-run: the aarch64 hosts and the LLVM Debug
mode (the comparison itself is host independent).
