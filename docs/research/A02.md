# A02 — Instruction semantics and target expansion

Status: research, with two recorded native probes and a backend probe
([ROADMAP](../../ROADMAP.md), [acceptance](../../remaining-acceptance.md#a02--instruction-semantics-and-target-expansion)).

## Question

Inline assembly is today an opaque register contract. Each accepted `(template, constraints,
clobbers, target)` is one entry of a reviewed allowlist (`Air2Lean/AsmAllowlist.lean`, 19 entries,
x86_64 plus the aarch64 `isb` spin hint). The translator emits `opaque airAsm_<hash>` (ASM-01), a
theorem that needs the instruction's behaviour states it as a hypothesis about the opaque
(ASM-02), and the entry's fault condition and the CPU's support for the instruction are premises
(ASM-04). A01 made the *effects* explicit (ASM-03, ASM-05, ASM-06: register-only, read-write,
environment reads, two `rep` string instructions). Nothing says what an instruction *computes*:
`bswap32_involutive` is proved from `hinv`, and the A03 interpreter that tests the wrappers is
hand-written from the Intel manual and "not hardware-validated" (AH-01).

The acceptance asks for selected verified instruction semantics or qualified contracts,
architecture-specific backends (ARM) only with matching register and effect rules, an
instruction's behaviour that is proved or marked as an assumption, and wrapper proofs reported
separately from instruction proofs. Which source of semantics, which targets first, and how do
instruction effects enter the one framework?

## What Zig does (pinned sources, 0.14.1 / 0.15.2 / 0.16.0 / 0.17.0)

- **Two assemblers behind one template.** The LLVM backend hands the template text to LLVM's
  integrated assembler (AT&T syntax on x86_64). The self-hosted x86_64 backend parses the same
  text itself (`src/codegen/x86_64/CodeGen.zig` `airAsm`, which converts AT&T to Intel
  mnemonics and looks them up in `encodings.zon`, 1993 lines in 0.17.0), and the self-hosted
  aarch64 backend (0.15.2 and later) has its own `Assemble.zig` over `instructions.zon` (5786
  lines in 0.17.0). The wasm backend has a 717-line assembler for a wasm text subset
  (`codegen/wasm/assembly.zig`). So the bytes executed for one template depend on the backend.
  These `.zon` files are encoding tables, not semantics, but they are a machine-readable
  cross-check for any decoder the translator grows.
- **Which backend is the default.** 0.14.1: LLVM unless `-fno-llvm`. 0.15.2 and later: the
  self-hosted x86_64 backend is the default in Debug on x86_64 ELF (`target.zig`
  `selfHostedBackendIsAsRobustAsLlvm`; 0.17.0 excludes macho and BSDs). The project qualifies only
  `ReleaseSafe` with `stage2_llvm` (`docs/build-modes.md`), so LLVM's assembler is the qualified one;
  the self-hosted encoder is a second assembler for the same source.
- **Feature-gated instructions differ by backend.** At the baseline CPU the self-hosted x86_64
  backend rejects `popcnt`, `lzcnt` and `rdrand` ("no encoding found ... emit MIR failed:
  InvalidInstruction (Zig compiler bug)", upstream draft 05, issue #131), and LLVM assembles them
  for any CPU. Recorded by `tests/roadmap/asm-semantics/check.sh` (0.17.0, x86_64-linux-musl).
  The profile that the exporter records (`profile.features`) already says which features the
  compile target has: the `asm_env` AIR (`tests/roadmap/asm-effects/air-env/0.17.0`) is exported
  with cpu `x86_64` and features `64bit cmov cx8 fxsr ... sse sse2 x87`, no `popcnt`, `lzcnt` or
  `rdrnd`. The allowlist accepts `rdrand` under it, and ASM-04 ("the CPU has the instruction")
  is a premise that nothing derives from the profile.
- **What std emits.** About 740 `asm volatile`/`asm (` sites in 0.17.0 `lib/std` and
  `lib/compiler_rt`, by class:
  - OS entry: `syscall` (x86_64) and `svc #0` (aarch64) in `os/linux/*.zig` (`syscall0..6`, with
    a `memory` clobber), `int $128`, `ecall`, ... The project cuts above these (`docs/thread-io-translation.md`
    B2, `docs/allocator-model.md`): `posix.mmap`, futex, clone are modelled at the named
    `os.linux.*` wrapper (OSM-01, ENV-03). They never enter an instruction table.
  - Process start, TLS, PIE relocation, context switch (`start.zig`, `os/linux/tls.zig`, `pie.zig`,
    `Io/fiber.zig`, `Io/Uring.zig`, `Io/Kqueue.zig`, `debug/cpu_context.zig`): below the program
    model. Out of scope and rejected.
  - compiler_rt `aarch64_outline_atomics.zig` (100 sites: `ldxr`/`stxr`/LSE `cas` loops): the
    implementation of atomics. The model already treats an atomic as a primitive operation
    (C12/ORD-06), so these stay below the cut line.
  - Hints and barriers: `pause`, `isb`, `yield` (`atomic.spinLoopHint`, done by C03), the empty
    template with an input (`mem.doNotOptimizeAway`: `""` with `"r"`, `"rm"` or `"m"` inputs, and a
    `memory` clobber for pointers). Rejected today because the allowlist matches the exact
    operand shape; an empty template has no instruction, so one rule covers all its shapes.
  - Compute kernels behind a comptime CPU-feature test: `crypto/aes/aesni.zig` and `armcrypto.zig`
    (`aesenc`, `aese`, `aesmc`), `ghash_polyval.zig` (`vpclmulqdq`, `pmull`), `sha2.zig` (`sha256rnds2`,
    `sha256su0`), `hash/crc/Crc32c.zig` (`crc32b/q`), `crypto` hardware paths. They are chosen by
    `builtin.cpu.has(...)`: `std.crypto.aes` picks the asm path only if `has_aesni and has_avx` or
    `has_armaes`, otherwise `aes/soft.zig`. The Apple M1 profile (`aarch64-macos`, cpu `apple_m1`) has
    `aes`, `sha2`, `crc` and `pmull` features, so a std SHA-256 or AES translation on that profile
    reaches vector inline asm (operands `"w"`, `"x"`, `@Vector`), which the allowlist rejects. The
    baseline x86_64 profile takes the pure-Zig paths and contains no asm at all.
  - wasm32 (`Thread.zig`, `Io/Threaded.zig`): `memory.atomic.wait32`, `notify`, `global.get`.
    These are Zig's own text syntax, and the program is not translated for wasm32 threads.
- **Versions.** 0.14.1's exporter exports no inline asm (A01), so every asm function is rejected
  there (fail closed). Clobber syntax changed from strings to the struct form in 0.15.2; the exporter
  normalizes it. 0.15.2, 0.16.0 and 0.17.0 export identical `assembly` instructions for the
  committed fixtures.

## Native observations (recorded, `tests/roadmap/asm-semantics`)

`check.sh` rebuilds both probes with the stock Zig 0.17.0 and compares with `expected_*.txt`.
The x86_64 probe runs in `docker run --platform linux/amd64` (Rosetta, so a smoke test, not
silicon: CI's x86_64 rows run on real CPUs and must carry the authoritative row); the aarch64 probe
runs on the host (Apple M-series).

- **x86_64, the allowlisted instructions.** `lzcnt(0)=64, lzcnt(1)=63, lzcnt(2^63)=0`,
  `popcnt(2^64-1)=64`, `divl 100/7 = (14, 2)`. `bsr(1)=0` and `bsr(2^63)=63`: `lzcnt`'s encoding
  runs as `bsr` on a CPU without LZCNT, so on such a CPU the allowlist's `lzcnt64(1)` is `0`, not
  the `63` the opaque contract is used for. That is the concrete scenario behind ASM-04's CPU half.
  `rdrand` returned two different values with the success flag set, and `rdtsc` is only weakly
  ordered under Rosetta (two reads may be equal). So "no relation between reads" (ASM-05) is
  the correct strength.
- **aarch64, the first candidates.** `rev`, `clz`, `rbit` and a NEON `cnt`/`addv` population
  count agree with `@byteSwap`, `@clz`, `@bitReverse`, `@popCount` on six inputs including 0, all
  ones and the top bit. `udiv x, 0` is `0`: no exception, where x86 `divl` faults (#DE). A port
  of the x86 `divmod` entry's shape (`AsmFault.zeroInput`) to aarch64 would model a trap that does
  not exist; fault conditions are per-ISA data and cannot be copied across targets.
  `mrs x, cntvct_el0` is readable at EL0 and monotone in the probe: an environment read like
  `rdtsc`, so ASM-05 generalizes with the instruction's attribute, not with its target.

## Options

1. **Keep the allowlist; add entries.** Each entry is reviewed prose plus an opaque and ASM-02
   hypotheses. Cheap and fail closed, but it does not scale to the std classes above (vector
   crypto, `crc32`), every theorem restates its instruction fact, and "an instruction's behavior is
   proved or marked as an assumption" is met only by the second half. Instruction behaviour stays
   unchecked by any tool (AH-01).
2. **Import a formal ISA model as a kernel dependency.** Arm A-profile: the Sail Arm models
   (`rems-project/sail-arm`, Armv8.5/9.3/9.4-A, automatically translated from Arm's own ASL,
   BSD-3-Clause-Clear) or AWS's LNSym (`leanprover/LNSym`, Apache-2.0, an Armv8 AArch64 formalization
   in Lean 4 with conformance testing against hardware, used for AWS-LC proofs). x86_64: Sail
   x86 models (translated from the ACL2 X86isa model, or a legacy hand-written user-mode
   fragment), the K semantics of x86-64 (Dasgupta et al., PLDI 2019), HOL4's L3 x86 model. Best
   provenance: the premise becomes "the ISA model is the architecture and the CPU conforms".
   Costs: Sail's Lean backend exists in the repository (`sail_lean_backend.opam`) but I could not
   establish its maturity or whether sail-arm builds with it (Lean, Coq, Isabelle/Lem are the
   documented prover targets); a whole-ISA import is far over the 12 GB build cap and brings
   system registers, exceptions and translation regimes the model does not use; LNSym covers
   AArch64 only. There is no vendor-authoritative machine-readable x86 specification: Intel's
   pseudocode is prose, and every x86 model above is a reconstruction validated by testing.
3. **A small trusted instruction subset with tests** (the A03 interpreter promoted to the
   semantics). Cheap and under our control; the trust is the author's reading of one manual.
   Without an independent source it repeats AH-01 at larger scale.
4. **Translation validation of the compiled output.** Disassemble the object code Zig produced
   and check it against the decoded template, or validate the machine code against the AIR
   semantics. This closes the assembler (second row of the table below), not the instruction
   semantics. Validating whole functions against AIR is V-lane work (V01/V02); it can reuse an
   instruction library but does not replace one.

## Recommendation

**An instruction-semantics library keyed by the decoded instruction, anchored to a formal ISA
specification and to hardware, replacing the opaque for every instruction it covers.** It is
option 3's shape with option 2's provenance, option 4's check on the assembler, and option 1 only
for what is not yet covered (unchanged fail-closed behaviour).

1. **Decode in the translator.** `Air2Lean` parses an accepted template into `Isa.Instr` values
   (AT&T x86_64 subset, AArch64 syntax): mnemonic, operand kinds, `%[name]` and `%%reg`
   substitution, optional `rep`. An unknown mnemonic or operand form is rejected with the current
   `ASM_VOLATILE_EFFECT` diagnostic (fail closed). The semantics are keyed by the decoded
   instruction, never by template text, so the two assemblers and the template's formatting do not
   matter. The decoded footprint (registers read and written, memory read and written) is computed
   statically and compared with the constraints and clobbers: a write to an undeclared register is
   a translation error. That turns the register half of ASM-03, which A03's interpreter only
   tests, into a checked fact.
2. **Semantics as ordinary Lean in `ZigLean/Isa/{Core,X86,A64}`.** A small machine state (general
   registers, vector registers as `BitVec 128`, the flag bits that matter), `Isa.step : Instr →
   State → MemM State` over `BitVec`. A fault is `throw .trap` in the step, exactly on the
   ISA's condition (so `Zig.asmTrap` and `AsmFault` disappear: the fault condition is part of the
   instruction, per ISA). An environment read queries `Mem.arbitrary` (ASM-05 as an instruction
   attribute). Memory operands and `rep` strings go through the checked `Zig.load`/`store`, so
   ASM-06's region contracts become *theorems* about `step` (`rep stosb` writes `rcx` bytes at `rdi`
   and nothing else), no longer premises. Anything not in the table, and every atomic or `lock`
   instruction until the concurrency model covers it (C12), stays rejected.
3. **Emit a defined function, not an opaque.** For a block whose instructions are all in the table
   the wrapper calls `Isa.block <instrs> inputs`, a `def`. Per-instruction equation lemmas in a
   simp set (`step_popcnt`, `step_lzcnt`, ...) let `fsym_norm` reduce it, so a theorem about
   `bswap32` no longer needs `hinv`. Wrapper structure (guard, loads, stores) is unchanged, so
   `Proofs/Asm/Effects.lean`'s frame lemmas still apply. ASM-01, ASM-02 and ASM-04 retire for
   covered blocks.
4. **Anchor the table to a spec and to silicon.** Every instruction entry carries its source
   (ASL/Sail instruction id, or SDM section for x86), a differential vector set, and where an
   executable spec exists, a check against it:
   - *Level A (CI, outside the kernel):* generate vectors from the Sail Arm C emulator and, for
     x86, from two independent models (Sail x86, K), compare with `#eval` of the Lean step and
     with native runs on the real CI CPUs (x86_64 hosted runners, aarch64 macOS). A mismatch fails
     the row.
   - *Level B (kernel):* for instructions where the Sail Lean output extracts, prove
     `step i = sail_i` per instruction (`bv_decide` for the bit-vector cores). Attempt it for Arm
     first; whether the Sail Lean backend and the arm models extract with acceptable size is the
     first spike (phase 4). No whole-model import.
5. **Check the assembler.** A CI row assembles each committed template with the stock Zig
   backends (LLVM, and the self-hosted ones where they accept it), disassembles the object code
   with the compiler's own `Disassembler.zig`, `Disassemble.zig` or objdump, and compares with the decoded `Isa.Instr`
   list. That is premise ASM-08 below, and it detects the cross-backend gap recorded above.
6. **Check the CPU requirement against the profile.** Each instruction entry names the CPU feature
   it needs (`popcnt`, `lzcnt`, `rdrnd`, `aes`, `crc`, ...). The translator compares it with the
   exported `profile.features`. If the feature is absent the program is rejected, unless the
   project passes an explicit admission (`--assume-asm-cpu-features=popcnt,lzcnt`, a premise like
   `--assume-no-libc`). Today's accepted fixtures are exported at the baseline CPU, so they would
   need the admission or a profile with the feature; that is intended, since ASM-04's CPU half
   becomes a visible, derived fact.

**Targets.** The mechanism is ISA-neutral. x86_64 migrates first because it carries the 19
existing entries and the A01/A03 tests, which are the regression suite. aarch64 follows and is
where Level B is attempted, because Arm's own ASL is the one authoritative machine-readable
source and the host hardware is aarch64 (every probe row is native). Order inside aarch64: the
`rev/clz/rbit/cnt/udiv/yield/isb/mrs cntvct` set above, then `crc32*`, then the crypto extension
(`aese`, `aesmc`, `pmull`, `sha256*`), which is what std reaches on the Apple profile. wasm32,
s390x and mips64 keep rejecting asm; wasm32's asm text is Zig's own language and belongs with
wasm32 threads (T05/C12 follow-ups).

**Where the std crypto kernels give a free oracle.** For `aes`, `ghash`, `sha2` and `crc32c`, std
carries a pure-Zig implementation (`aes/soft.zig`, the table `Crc32c`, the portable round). The
project translates real Zig, so the translated soft path is an independent, hand-free oracle for
the instruction: the acceptance client proves (or tests, for 64-round SHA) that the hardware
instruction sequence equals the translated soft round. This follows the Trusted-base rule (no
hand-written model of a std module).

## Why not the alternatives alone

- Option 2 alone is the end state for Arm but not a plan: no x86 spec of equal standing exists,
  whole-model import does not fit the build cap, and the template-to-instruction decode and the
  footprint check are needed whatever the source of semantics.
- Option 3 alone has no independent source (AH-01 again). It is acceptable as the carrier of the
  semantics only with the anchors in step 4.
- Option 1 is what exists; it is kept as the fail-closed fallback for any instruction without a
  table entry.

## How it fits the one proof framework

No new judgment, tactic, template or automation.

- `Isa.step` and `Isa.block` are `MemM` computations. `fsym` already walks `Zig.load`/`store`,
  `pure`, `throw`, and calls; the only additions are **lemmas**: a simp/`fsym_norm` set of
  per-instruction equations, and for `rep` instructions an `@[fsym]` call rule stating the region
  frame (the same shape as the allocator call rules), proved from the step definition and `FTriple`
  loop rules. Register-only blocks are `pure` terms and are normalized, not stepped.
- A theorem about a function containing asm is an ordinary `FTriple`/`FTotalTriple`; the wrapper
  lemmas are the existing frame lemmas, the instruction lemmas are the `Isa.*` equations. They
  are separate declarations, in separate modules (`ZigLean.Isa.*` is a new `runtime_modules`
  entry), so `scripts/claims.py` can list the instruction premise (ASM-07) apart from the wrapper
  premises (ASM-03), as the acceptance requires; the C12 mechanism (per-theorem `runtime_modules`
  from the audit) does the mapping, with no new code path beyond the module mapping.
- If `fsym` cannot discharge a covered block (for example a vector register state with 128-bit
  `BitVec` normalization), the work stops with the exact missing normalization rule per
  CLAUDE.md. A03's `Interp.lean` `Spec` structure is on the legacy list; replacing the
  interpreter by `Isa.step` run with `#eval` deletes it.

## Fail-closed behaviour until implemented

Unchanged: an asm not matching an allowlist entry is `ASM_VOLATILE_EFFECT`; wasm32, s390x and
mips64 reject asm; aarch64 accepts only `isb`; 0.14.1 exports none. Phases 1 and 2 keep this
and add rejections (undeclared register write; feature missing from the profile). No phase
may accept a construct that is not yet decoded and modelled.

## Premises

Existing: ASM-01, ASM-02, ASM-04 retire per covered block (kept for uncovered allowlist
entries); ASM-03's register half is checked statically for covered blocks, its memory half stays;
ASM-05 becomes an attribute of the instruction (`rdtsc`, `rdrand`, `cntvct_el0`); ASM-06 is
derived for covered `rep` instructions. Proposed, not yet in the catalogue (they enter
`docs/premises.md` and `assurance/premises.json` with phase 2, with their token rules):

| ID | Kind | Statement |
|---|---|---|
| ASM-07 | trusted | `ZigLean.Isa.<arch>` gives each covered instruction the ISA's semantics, including its fault condition, on a CPU that has the instruction's feature. Qualified per instruction by its provenance record (spec id, Level A vector set, Level B lemma where it exists, hardware rows). |
| ASM-08 | trusted | The assembler of the qualified backend encodes the template as the decoded instruction list (validated by the CI assemble-and-disassemble row; the self-hosted backends are separate rows). |
| ASM-09 | admission | `--assume-asm-cpu-features=...`: the running CPU has the named features although the profile's CPU does not list them. |

## Acceptance evidence that would close the row

1. All 19 allowlist entries are decoded and modelled; `Air2Lean/AsmAllowlist.lean` holds no
   `.opaque` entries (only the barrier registry and device events).
2. For each covered instruction: a provenance record; a kernel-checked equation lemma; a
   differential row against native execution on real x86_64 and aarch64 CPUs in CI. For Arm, at
   least the integer and crypto instructions carry a Level B lemma against the Sail extract, or
   the spike's negative result is recorded with the reason.
3. `scripts/claims.py` emits ASM-07 (with table version) separately from wrapper premises; a test
   shows a goal about `bswap32` reports no ASM-02 hypothesis.
4. Fail-closed tests: unknown mnemonic, undeclared register write, feature absent from the profile
   (with and without the admission), `lock`-prefixed instruction, an asm assembled differently by
   the self-hosted backend.
5. A real client: `Crc32c` (x86 `crc32q`, aarch64 `crc32cx`) equals the translated table-driven
   software `Crc32c` for all inputs, or SHA-256 `round` on the Apple profile equals the portable
   round; it is stated over the instruction library, not over a hypothesis.

## Decisions for the maintainer

1. Confirm the replacement of `opaque airAsm_<hash>` by a defined function for covered blocks
   (regenerates `Proofs/Asm/Gen.lean` and the asm goldens; names stay hash-keyed).
2. Confirm that a program using a CPU-feature instruction not in the profile's feature list is
   rejected unless `--assume-asm-cpu-features` is given (today's fixtures need the flag or a
   `-mcpu` with the feature).
3. Licence and pinning for the Sail Arm/ASL sources: vendor only the generated vectors and the
   extract, pin sources by hash in `assurance`, and check Arm's ASL licence before any vendoring
   (not verified here).

## Not verified here

Sail Lean backend maturity and sail-arm's ability to use it; LNSym's instruction coverage; the K
x86-64 semantics' current availability; hardware behaviour on real silicon for the Rosetta rows.
Each is the first task of the phase that depends on it, and none changes the recommendation, which
is written so that Level B is optional per instruction.
