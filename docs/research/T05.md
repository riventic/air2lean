# T05 — Native and WASM correspondence

Status: research, with a checked relation over paired fixtures
([ROADMAP](../../ROADMAP.md), [acceptance](../../remaining-acceptance.md#t05--native-and-wasm-correspondence)).

## Question

A theorem about a generated module is about the analyzed AIR of one recorded profile (PRF-02,
PRF-04). When the same Zig source also ships as wasm32, what may be claimed about the wasm32
build, and on what evidence? The acceptance asks for paired target fixtures, a precise
observation relation, target-independent contracts for qualified integer and discrete-event
(DES) kernels, and tolerances for numerical code. Equivalence claims must tell apart exact
outputs, tolerated differences and target-specific effects. No native theorem may be relabeled
as a wasm32 theorem.

## What differs between a native target and wasm32

- **Pointer width.** `usize`, pointers, slices and allocation limits are 32-bit on wasm32
  (T02, `Zig.PtrWidth`). Any `usize` boundary moves: `4 * n` overflows at `n = 2^30`, and an
  increment panics at `2^32 - 1`.
- **Floats.** wasm32 has IEEE-754 `f32`/`f64` arithmetic with correct rounding, like the native
  targets. A NaN result's sign and payload are not specified (x86_64 makes the default NaN
  negative, wasm32 and aarch64 positive). `@mulAdd` is a compiler_rt call on wasm32 and an
  instruction natively; both round once. libm functions (`@sin`, ...) are compiler_rt on wasm32
  and Linux without libc, and the platform libm on macOS. They are faithfully rounded, not
  correctly rounded. `c_longdouble` is `f128` on wasm32, `f80` on x86_64.
- **Illegal behaviour that safe mode does not detect.** The result of illegal behaviour is not
  defined, and it does differ: `@intFromFloat` of a NaN gives `minInt` on x86_64 and `0` on
  aarch64 and wasm32 (see Findings).
- **Panics.** A safety panic is a process abort natively and an `unreachable` trap on
  wasm32-freestanding. The panic message is not observable on wasm32-freestanding.
- **Concurrency.** The translator rejects atomics, threads and futexes on wasm32 (T02). wasm32
  threads would need the shared-memory proposal and their own memory-model argument (C12).

## Options

1. **Relabel native theorems for wasm32.** Treat a theorem about the x86_64 translation as
   evidence for the wasm32 build when the source is the same. This is unsound for every
   width-dependent result (the `byteCount` and `succ` boundaries above) and it hides NaN and
   libm differences. Rejected; the acceptance forbids it.
2. **Differential testing only.** Run both builds on the same inputs and require equal outputs.
   This is cheap, but "equal" is wrong for floats (NaN bits, libm ulps) and for every
   width-dependent kernel, and it says nothing about the inputs that were not run.
3. **A compiler correspondence proof** for the wasm32 backend (LLVM's WebAssembly lowering).
   This is the strongest option and out of reach: no part of the pipeline has a backend
   preservation theorem (TRU-03), on any target.
4. **Per-profile proofs, with a classified observation relation as qualification evidence.**
   Every theorem stays about the translation of one recorded profile. A target-independent
   contract is a Lean statement parameterized by the profile's facts (pointer width, float
   rules), proved once against the width-parameterized semantics and instantiated per profile.
   A wasm32 claim needs a wasm32 translation and a theorem about it. Native and wasm32 builds
   of one source are related by an explicit relation in which each observation has one
   class: **exact**, **tolerated** (a declared float tolerance) or **target-specific** (each
   side meets its own profile's model, the two sides are not compared with each other).
   Illegal-behaviour inputs that safe mode does not detect are excluded, as the model's
   `.illegal` allows any result. A checker applies the relation to recorded observations and
   fails closed.

## Recommendation

Option 4. It supports the whole language because nothing in it is kernel-specific: the
relation is declared per export and the checker treats every export the same way; the semantic
side reuses the general width-parameterized model (`ZigLean/Mem/Width.lean`) and its general
lemmas, not per-snippet proofs. It keeps the trust base honest: the relation is qualification
evidence for TRU-03 on each target, never a substitute for a per-profile theorem. And it is the
shape a future backend proof would plug into: the relation's classes are exactly what such a
proof would have to state.

The long-term steps are:

1. Accept wasm32 for the remaining T02 rejections (atomics need C12's wasm argument first;
   `@tagName`/`@errorName`, vectors in memory, Io) so that more kernels have a wasm32
   translation.
2. State target-independent contracts as width-parameterized theorems (as
   `PointerWidth/Proofs.lean` does per width today), with one proof for both instances.
3. Grow the paired fixtures toward whole programs: the DES queue kernel here is the start; a
   translated wasm32 build of a case study (Flow's `addDuration`) is the next.
4. Re-observe every record in CI: today the `native` part re-observes the 0.16.0 x86_64-linux and
   wasm32 records; the 0.17.0, 0.15.2 and 0.14.1 and the aarch64-macos records are re-observed
   locally (`record --verify`), and `check` runs on all of them.

## Implemented

- `tests/roadmap/wasm-correspondence/kernels.zig`: one source of exports `u64 -> u64` (signed
  values and float bits are bit-cast inside, so the drivers pass plain words): DES kernels
  (Flow's `addDuration` rule at `u32`/`u64`, event order, a binary-heap event queue), integer
  kernels (wrapping arithmetic and bit builtins, `i64` division, checked add and shift), the T02
  `pointer_width.byteCount`/`succ` functions and `@bitSizeOf(usize)`, and float kernels
  (`+ * /`, `@sqrt`, `f32` `@mulAdd`, `@sin`, `@intFromFloat`).
- `relation.json`: the class of each export with the reason it holds; the input domains (edge
  values, then seeded random draws); the version × target matrix; and the claims that bind a
  kernel on a target to a theorem.
- `scripts/wasm-correspondence.py record` builds the source with a stock compiler as a native
  shared library (driven by `ctypes`, a forked child per panic) and as a wasm32-freestanding
  module (driven by Node, `run-wasm.mjs`, a fresh instance after each trap). A record binds the
  compiler, the source bytes and the cases. `record --verify` re-observes and compares.
- `scripts/wasm-correspondence.py check` (CI, the `inputs` part) applies the relation to every
  recorded pair: exact equality, float tolerance (`ulp`, any NaN with any NaN), or each side
  against its profile model (`expect`, a closed expression over the arguments and the
  profile's `bits`). It fails on an export without a class, a class without an export, a
  missing or stale record, an unrelated pair, and a claim whose theorem is not about a
  generated module of the claim's target (`byteCount_x64` cited for wasm32, a theorem that
  mentions both targets, or the x86_64 Flow case study cited for a wasm32 kernel).
- Records: Zig 0.17.0 and 0.16.0 on x86_64-linux (Docker `linux/amd64`), aarch64-macos and
  wasm32; 0.15.2 and 0.14.1 on x86_64-linux and wasm32. The stock 0.14.1 and 0.15.2 compilers
  cannot link a macOS dynamic library on the current macOS SDK, so those two versions are not
  declared for aarch64-macos.

Per pair, about 2700 exact, 1330 tolerated and 160 target-specific observations hold. The
wasm32 claims cite `byteCount_w32` and `succ_w32`, proved about the wasm32 translation;
the x86_64 claims cite `byteCount_x64` and `succ_x64`.

## Findings

- **`@intFromFloat` of a NaN is not detected in ReleaseSafe** by Zig 0.15.2, 0.16.0 and 0.17.0 on
  any of the three targets. x86_64 returns `minInt(i64)`, aarch64 and wasm32 return 0. The model
  already makes this `.illegal` (docs/floats.md), so no theorem is affected; the relation
  excludes these inputs (`illegal`).
- **Zig 0.14.1 on wasm32 does not detect `@intFromFloat(2^63)` to `i64`** (it saturates to
  `maxInt`; x86_64 panics). 0.14.1 has no out-of-range check in the model either
  (`int_from_float`, `.illegal`); the relation excludes out-of-range operands before 0.15.2.
- `@sin` differs by one ulp between macOS libm and compiler_rt, and between 0.14.1's x86_64 and
  wasm32 builds, within the declared tolerance.
- A NaN's sign differs between x86_64 and wasm32 on every float kernel (tolerated by class).

## Not claimed

The relation is bounded evidence on the recorded inputs, not a correspondence proof. It does not
cover wasm32-wasi system calls, threads or shared memory, wasm32 stack exhaustion, or
ReleaseFast/ReleaseSmall (T06).
