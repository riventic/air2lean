# F03 — Fast math and permitted transformations

Status: research, with recorded native observations of the divergence and a proposed
specification ([ROADMAP](../../ROADMAP.md),
[acceptance](../../remaining-acceptance.md#f03--fast-math-and-permitted-transformations)).

## Question

`@setFloatMode(.optimized)` lets the compiler change float results. The translator rejects every
`*_optimized` AIR tag today (`OPTIMIZED_UNSUPPORTED`; the profile requires
`float_mode: per-instruction`). What does Zig emit, per version, what may the native result be,
and how can a proof state "for every permitted result" instead of the model's one deterministic
choice? The acceptance asks for the allowed behaviours of each selected mode and flag (NaN, inf,
zero assumptions, contraction), strict-mode proofs kept separate, and proofs that quantify over
the allowed results or establish stronger preconditions. Deleting the rejection without semantics
does not count.

## What Zig does

Sources: the pinned compiler sources of 0.14.1, 0.15.2, 0.16.0 and 0.17.0 (shared CAS).

- **Sema.** `@setFloatMode` sets `block.float_mode` for the scope and its children (`strict`
  default; `std.builtin.FloatMode`, `std.lang.FloatMode` in 0.17.0). Nothing else selects it:
  ReleaseFast does not, and no CLI flag does (`docs/build-modes.md` "Changed semantics"). In
  optimized scopes Sema emits the `_optimized` twin of `add`, `sub`, `mul`, `div_float`,
  `div_trunc`, `div_floor`, `div_exact`, `rem`, `mod`, `neg`, `cmp_{eq,neq,lt,lte,gt,gte}`,
  `cmp_vector`, `reduce` and `int_from_float` (19 tags; 0.17.0 adds `div_ceil_optimized`, 20; these
  are the `rejected-fast-math` column of `docs/support-matrix.md`; 0.15.2+ also has
  `int_from_float_optimized_safe`). Everything else has no twin and is strict in both modes:
  `@sqrt`, `@sin`..., `@mulAdd`, `@min`/`@max`, `@abs`, rounding builtins, `float_from_int`,
  `fptrunc`/`fpext`, and comptime evaluation (always IEEE).
- **Safety checks change.** Float division by zero is a panic in optimized scopes where safety is
  on (`addDivByZeroSafety`, a `cmp_neq_optimized` against zero) and an IEEE result in strict ones
  (`docs/illegal-behavior.md`). `@divExact` checks its remainder with `cmp_eq_optimized`.
  `int_from_float_optimized_safe` legalizes into range checks that are themselves optimized
  compares (`Air/Legalize.zig`, `safeIntFromFloatBlockPayload`), so a NaN operand is not
  reliably caught.
- **LLVM backend.** `FastMathKind.fast` is `Builder.FastMath.fast`: `nnan ninf nsz arcp contract
  afn reassoc` (the legacy `unsafe_algebra` bit is not set), byte for byte the same in all four
  versions. It is put on `fadd/fsub/fmul/fdiv/frem`, `fcmp`, `select` (`@mod`), and calls to the
  `trunc/floor/ceil/fmin/fmax` intrinsics inside `@divTrunc`/`@divFloor`/`@divCeil` and the
  `vector.reduce.f{add,mul,min,max}` of `reduce`. Not flagged: `fneg` (so `neg_optimized` is a
  plain `fneg`), `int_from_float` (`_ = fast`; 0.17.0 keeps "TODO set fast math flag"), and every
  op that reaches compiler-rt or libm because the float type has no hardware or intrinsic support
  (`buildFloatOp` drops `fast` on the soft-float path), e.g. `f128` on x86_64. `afn` therefore
  has no observable effect from Zig: no libm-class call carries it.
- **Other backends.** The C backend fails with "TODO implement optimized float mode" on all of
  these tags. The self-hosted x86_64 backend (the default for Debug on x86_64-linux since 0.15)
  lowers them with its own sequences; the observed difference is the compare (`NaN != NaN` is
  `false`). The identity rewrite is always a member of the permitted set, so a backend that does
  not rewrite stays inside it.
- **Zig 0.14.1 only: Sema folds `x + 0.0` to `x` even in strict mode**, so `-0.0 + 0.0` is
  `-0.0` (a bug; draft `docs/upstream/float-add-zero-fold.md`). The AIR has no `add`, the model
  translates the AIR, so nothing in air2lean is wrong; MTH-01's IEEE claim just does not describe
  that source construct on 0.14.1.

## What the flags permit

LLVM LangRef ("Fast-Math Flags", main as of 2026-10), against Zig's langref bullets
(`@setFloatMode`):

| Flag | Meaning | Zig langref | Probe case (`probe.zig`) |
|---|---|---|---|
| `nnan` | A NaN operand or result is poison | "assume not NaN ... value of the result is undefined" | `self_ne`, `nan_lt`, `mul_zero_nan`, `sub_self` |
| `ninf` | An infinite operand or result is poison | same for infinities | `eq_inf`, `mul_zero_nan`, `sub_self` |
| `nsz` | The sign of a zero operand or result is free | "sign of a zero is insignificant" | `mul_zero`, `add_zero` |
| `arcp` | `a / b` may be `a * (1 / b)`, `a / (b / c)` may be `a * (c / b)` | "use the reciprocal" | `div_three` |
| `contract` | A multiply feeding an add/sub may fuse into one rounding | "floating-point contraction" | `fma_shape` |
| `reassoc` | Any algebraically equivalent transformation | "algebraically equivalent ... reassociate" | `sum`, `sum_cancel` |
| `afn` | Approximate library functions | none | none (never reachable, see above) |

Two points decide the design.

1. **Poison is stronger than Zig's wording.** The langref says the result's *value* is
   undefined and "legal behavior is retained". LLVM makes it poison, and a branch on poison is
   undefined behaviour. The probe shows the effect: `nan < 1.0` is `true`, `x != x` is `false`,
   `inf == inf` is `false`, `inf * 0.0` and `inf - inf` are `0.0`. The model has to cover what
   runs, so NaN/inf reaching an optimized op must be `.illegal` (CLAUDE.md "Fail closed": an
   over-approximation, to be documented where it is introduced), not "an unspecified float".
2. **The rewrite flags act on regions, not on operations.** LangRef: a rewrite needs the flag on
   *every* instruction in the expression, instructions need not be adjacent, and the rewritten
   code carries the intersection of the flags. The region is a connected part of the *dynamic*
   dataflow of flagged instructions: through loop-carried values (the vectorizer's reduction
   reordering), through inlined calls, and through memory once the optimizer has forwarded it.
   A set of results per operation cannot describe that. `sum_cancel` is the witness
   ([Evidence](#evidence)): the strict partial sums of `[1e16, -1e16, 1, ..., 1]` never exceed 62
   in magnitude, so any bound built from the operands of each operation is within about 1e-12 of 62,
   and the optimized loop returns 60.

Also: two uses of one flagged SSA value need not see the same bits. `contract` may fuse the
multiply into one use and keep the rounded product for another; the optimizer may duplicate an
instruction and rewrite each copy. A model with one variable per fast result proves facts such as
`t == t` that native code does not have.

## Evidence

`tests/roadmap/fast-math/` (checked by `check.py`, which needs no Zig): `probe.zig` builds each
case twice, `.strict` and `.fast`, from one body that differs in `@setFloatMode`; operands are
runtime values. `observe.py` runs it natively and writes `records/`: Zig 0.17.0, 0.16.0 on
aarch64-macos; 0.17.0, 0.16.0, 0.15.2, 0.14.1 on x86_64-linux in `--platform linux/amd64` Docker
(baseline CPU and `x86_64_v3`), each in Debug, ReleaseSafe and ReleaseFast. (The stock 0.14.1 and
0.15.2 compilers cannot link a macOS dynamic library on the current SDK; as in T05 they are not
recorded for aarch64-macos.) Results of ReleaseFast, Zig 0.17.0, strict -> fast:

| Case | strict | fast | Flags |
|---|---|---|---|
| `sum` ([1e16, 62 x 1.0, -1e16]) | `0.0` | `60.0` | reassoc |
| `sum_cancel` ([1e16, -1e16, 62 x 1.0]) | `62.0` | `60.0` on aarch64; `62.0` on x86_64 | reassoc |
| `fma_shape` (`a*b + c`, `a*b = 1 - 2^-54`) | `0.0` | `-2^-54` | contract |
| `div_three` (`x / 3.0`) | `...efb1` | `...efb0` | arcp |
| `mul_zero` (`-1.0 * 0.0`) | `-0.0` | `+0.0` | nsz |
| `add_zero` (`-0.0 + 0.0`) | `+0.0` | `-0.0` (0.15.2+; 0.14.1 folds both) | nsz |
| `nan_lt` (`NaN < 1`) | `false` | `true` | nnan |
| `self_ne` (`NaN != NaN`) | `true` | `false` | nnan |
| `eq_inf` (`inf == inf`) | `true` | `false` | ninf |
| `mul_zero_nan` (`inf * 0`) | NaN | `0.0` | nnan, ninf |
| `sub_self` (`inf - inf`) | NaN | `0.0` | nnan, ninf |
| `gt_max`, `sqrt_neg`, `mul_add`, `div_trunc` | equal | equal | no twin or no effect |
| `div_zero`, `div_zero_zero` | inf, NaN | Debug/ReleaseSafe: panic; ReleaseFast: inf, NaN | safety check |

In ReleaseSafe and ReleaseFast nine cases diverge on every record (`sum`, `fma_shape`,
`div_three`, `mul_zero`, `nan_lt`, `self_ne`, `eq_inf`, `mul_zero_nan`, `sub_self`), `add_zero` on
0.15.2 and later, and `sum_cancel` on aarch64 only. Debug (no LLVM optimizer) differs only by the division panic,
and on x86_64-linux 0.15.2+ by `self_ne`, where the self-hosted backend assumes no NaN. `fma_shape` fused on the
baseline x86_64 CPU as well as on `x86_64_v3` and aarch64. `mul_add` (`@mulAdd`) is the same in
both modes: contraction cannot change a fused op. `sum_cancel` shows a set, not a function: two
targets, two permitted answers.

## Options

1. **Keep rejecting.** Sound and fail-closed, supports nothing; the row cannot close.
2. **Translate `_optimized` as the strict op.** Unsound: nine of the probe's cases are
   counterexamples (a kernel-checked theorem about the strict translation, e.g. "the sum is 0",
   is false of the native program). Rejected.
3. **A permitted-result relation per operation** (the `Float.Allowed` pattern of F04): nsz flips,
   the `arcp` reciprocal, a fused alternative for each multiply-add pair. Exact for `nsz` and
   single-operation `arcp`, but unsound once two flagged operations are connected
   (`sum_cancel`), which is every realistic fast-math loop. It is only sound with a checked
   isolation property (no flagged result reaches a flagged operand), which cannot be decided
   statically through memory, loops and calls, and rejects the code fast-math exists for.
4. **Region semantics with a real-valued envelope, proof-side only (recommended).**
5. **Verify the optimized LLVM IR or machine code.** Out of reach and out of the trust model
   (TRU-03: no backend preservation theorem, for any mode).

## Recommendation

Option 4, in the architecture F04 already set: the generated code calls a deterministic
executable model, and the permitted set exists only for proofs. Concretely:

1. **Model.** An `_optimized` tag becomes one wrapper per operation (`Zig.Float.fast.add`, ...)
   defined as the strict operation guarded by `.illegal` for a non-finite operand or result, and
   marked `@[irreducible]` so that `fsym` never unfolds it to the strict result. The
   executable meaning (differential tests, `#eval`) is the strict result, which is always a
   permitted result. Every *use* of a flagged value goes through `Zig.Float.fast.observe`, an
   identity at run time, so that two uses of one SSA value may differ (rematerialization). A
   function without `@setFloatMode(.optimized)` emits what it emits today: strict proofs and
   goldens do not change.
2. **Specification, a library (`ZigLean/Float/Fast.lean`).** `FExpr`: the real-valued expression
   over the leaves (non-flagged floats: parameters, loads, constants, strict results), with
   `real e : Rat`, the leaf-absolute sum `abs e` and an op count `size e`. `Float.Fast.Permitted
   e r`: `r` is finite and `|r - real e| <= gamma(size e) * abs e` (`gamma n = n*u / (1 - n*u)`
   from F06's `unitRoundoff` plus the underflow term), with the sign of a zero free. A single
   soundness lemma, from F06's `roundRat_error`, shows that every IEEE evaluation of any
   association, vectorization or contraction of `+ - *` and `neg` over the leaves is
   `Permitted`. Division and `arcp` get relative-error lemmas in a second step (`div_error`
   exists).
3. **Proof rules (`@[fsym]`).** `FastVal r e` is a pure assertion (`r` is `Permitted e`), not a
   heap resource. One rule per wrapper: `FastVal a ea -> FastVal b eb -> FastVal (fast.add a b)
   (ea + eb)` with the finiteness premise `abs e * (1 + gamma) < 2^emax` for the overflow of any
   rewrite; a leaf rule for strict values; a rule for `observe` giving an independent
   `FastVal r' e`; compare rules like F06's `lt_of_error` for a branch on a flagged value
   (the proof splits on both outcomes unless the envelope decides). Loops carry `FastVal s
   (leafSum prefix)` as the invariant, and the exit gives the usual `|s - sum| <= gamma_n * sum
   |x_i|` for every evaluation order. Termination, cost and allocation are untouched: the
   resources of `FTotalTriple`/`CTriple` apply as for any code. No new judgment, tactic or
   template is introduced.
4. **Labels.** Theorems get the float-semantics label `fast-envelope@<flags>` next to
   `ieee`/`compiler-rt`/`abstract-spec` (F01, `assurance/float-semantics.json`), and a claim lists
   MTH-09.

The soundness argument has two halves and the doc keeps them apart. *Inside Lean:* every rule is
derivable from the deterministic model plus the fact that the strict result is `Permitted`, and
proofs cannot use more because the wrappers are irreducible. *At the boundary:* that every
native result is `Permitted` is the premise MTH-09, backed by a review of the LLVM passes that act
on the flags (Reassociate, InstCombine, vectorizer reduction reordering, the DAG combiner's FMA
formation) and the differential relation below, not by a theorem (TRU-03).

Why the envelope and not the syntactic rewrite closure: the closure is unbounded (factoring,
distribution, constant folding) and each addition to what LLVM does would silently widen it; the
envelope is a decidable superset, so a membership check on a native observation is a computation,
and its slack is stated, not implicit. The cost is weaker theorems (error bounds, not exact
values) and a stated limit: the envelope covers rewrites that keep the polynomial's absolute
sum within a factor the lemma states; a rewrite outside it is a counterexample to MTH-09, not a
silent hole.

## Fail closed until implemented

Unchanged and already in place: the normalizer rejects each `*_optimized` tag first, with the
reason and guidance (`optimizedFloatGuidance`), before any other tag handling; profiles require
`float_mode: per-instruction`; `scripts/build-modes.py check` fails if a qualified source uses
`@setFloatMode`. Phase 1 below keeps rejecting every tag it does not cover (division, `rem`,
`mod`, vectors, `int_from_float`).

## Premises

- **MTH-01** (existing): strict IEEE model. Its wording "no optimization mode is qualified" stays
  true; fast-math theorems are not MTH-01 theorems.
- **TRU-03** (existing): no backend preservation theorem.
- **MTH-09, proposed** (environment): in a scope with `@setFloatMode(.optimized)` the flagged
  operations are exactly those of the table above with LLVM's `fast` flags (Zig 0.14.1 to
  0.17.0), and every native result, on every backend that accepts the tags, lies in
  `Permitted e`. Sources: the Zig backend sources, LangRef, `tests/roadmap/fast-math`.
- **MTH-10, proposed** (environment): a flagged operand or result that is NaN or infinite, in
  any association the compiler may choose, makes the program's behaviour undefined (the model
  says `.illegal`). Zig's langref is weaker (an undefined value); LLVM's poison is what runs.

## Acceptance evidence that would close the row

1. A real client under `@setFloatMode(.optimized)`: a dot product or `std.mem` sum loop whose
   theorem is the envelope bound, checked by `fsym` through the generated code, for all four
   versions.
2. A kernel-checked negative result: the strict value (`sum_cancel = 62`) is *not* provable, with
   a `Permitted` witness `r != 62`.
3. The differential relation: `check.py` extended so that each recorded native result is tested
   for `Permitted` membership (computable), next to the exact comparison used for strict code.
4. Rejection fixtures for what is not covered, the strict goldens byte-identical, MTH-09/07 in
   `docs/premises.md` and `assurance/premises.json`.

## Not claimed

The records are observations of four compiler versions on two targets, not a bound on what any
LLVM version may do. Nothing here supports fast-math code yet; the rejection stands.
