# C10 — Sequential consistency and unordered operations

Status: research ([ROADMAP](../../ROADMAP.md), [acceptance](../../remaining-acceptance.md#c10--sequential-consistency-and-unordered-operations)).
Builds on [C12](C12.md) (memory-model adequacy, premise [ORD-06](../premises.md#ord-06)).

## Question

The model's atomics (`ZigLean/Mem/Thread.lean`) approximate RC11 without promises. Two orderings
are not modelled as the language defines them:

* `seq_cst` has the rule of `acq_rel`: there is no global SC order
  ([ORD-03](../premises.md#ord-03)). A proof that needs it (store buffering, Dekker, IRIW,
  2+2W) does not go through.
* `unordered` is rejected, except for a load of an integer or pointer under
  `--allocator-model translated` (`Air2Lean/Check.lean`, `ZigLean/Conc/AtomicWord.lean`,
  [ORD-01](../premises.md#ord-01)). An `unordered` store is always rejected.

What does Zig 0.17.0 (first) and 0.16.0/0.15.2/0.14.1 define for each, which semantics should
the executable model and the full-state logic have, and how does a litmus proof tell relaxed,
acquire-release and SC outcomes apart? Acceptance: litmus proofs distinguish relaxed,
acquire-release and SC outcomes; stronger rules never remove an outcome the chosen target model
permits without justification.

## What Zig does (all four versions)

Sources: `Sema.zig` of the pinned compilers (`~/.cache/air2lean/cas/src`), native probes
(`/tmp`, recorded below).

* `std.builtin.AtomicOrder` (0.17.0: `std.lang.AtomicOrder`) is `unordered, monotonic, acquire,
  release, acq_rel, seq_cst`, mapped one to one to LLVM's orderings
  (`toLlvmAtomicOrdering`; 0.17.0: `codegen/llvm/FuncGen.zig`).
* Sema accepts `unordered` only in `@atomicLoad` and `@atomicStore`. `@atomicRmw` fails with
  "@atomicRmw atomic ordering must not be unordered"; `@cmpxchgStrong/Weak` with "success atomic
  ordering must be monotonic or stricter" (probed on 0.14.1, 0.15.2, 0.16.0, 0.17.0: same
  messages). A load may not be `release`/`acq_rel`, a store not `acquire`/`acq_rel`; a
  `cmpxchg` failure order may not be `release`/`acq_rel` nor stronger than the success order.
  An `unordered` store has its own AIR tag (`atomic_store_unordered`); an `unordered` load is
  `atomic_load` with `order: unordered`.
* **There is no fence.** `@fence` was removed in 0.14.0 (`std.atomic.fence` is a
  `@compileError` in 0.14.1 and absent after): all four versions answer "invalid builtin
  function: '@fence'". The translator also rejects a fence written as inline asm
  (`ASM_VOLATILE_EFFECT`, `docs/volatile-effects.md`). So the SC order of a Zig program consists
  of SC *accesses* (loads, stores, RMWs, `cmpxchg` with an SC success or failure order) only.
  RC11's SC-fence rules, and their known weak points, are out of scope until a Zig version
  brings a fence back.
* `unordered` is used by real std code, so rejecting it blocks translation, not only proofs.
  `std.Thread.Mutex.DebugImpl` (0.14.1 and 0.15.2 only; `Thread/Mutex.zig` is gone in 0.16.0:
  `locking_thread.load/store(.., .unordered)` in `lock`/`tryLock`/`unlock`, and in `Condition` on
  Windows): every `Mutex` in a Debug build.
  `std.heap.defaultQueryPageSize` (`cached_result.load/store(.unordered)`, 0.14.1 to 0.17.0),
  `SmpAllocator.getCpuCount`, `ArenaAllocator.endResize` (0.16.0), `Io.Threaded.lockStderr`
  (`stderr_mutex_locker`, 0.16.0 and 0.17.0, load and store), `os.linux.clock_gettime`'s vDSO
  pointer (all versions). The translated-allocator mode admits the loads of the page allocator
  and the arena; none of the stores.
* The self-hosted x86_64 backend (0.17.0: `codegen/x86_64/CodeGen.zig`, `atomicOp`) lowers like
  LLVM: an `unordered`, `monotonic`, `release` or `acq_rel` store is `mov`, a `seq_cst` store is
  `xchg`; loads are `mov`. ORD-06's argument (the RC11 mappings to x86-TSO and ARMv8) therefore
  also covers Debug builds there. Not checked for the other self-hosted backends (aarch64,
  riscv64, ...); they are outside the qualified targets.

## What the model does today, with evidence

`tests/roadmap/sc-order/` (this PR) holds a paired fixture like T05's.

* `sc.zig` is the native litmus program (the harness of T04's `weak-ordering/litmus.zig`,
  200 000 rounds). `observed/` holds its output on aarch64-macos (Apple M5 Pro), aarch64-linux
  (native `linux/arm64` container) and x86_64-linux (`linux/amd64` container under Rosetta), Zig
  0.17.0, ReleaseSafe, baseline CPU.
* `Sc.lean` computes, for the same tests, the model's outcome set (every interleaving, every
  oracle option of `atomicLoadAt`/`atomicStoreAt`) and the outcome set of the sequential
  interleavings of the same operations (RC11's outcomes when every access is `seq_cst`). Run:
  `lake env lean --run tests/roadmap/sc-order/Sc.lean tests/roadmap/sc-order/observed/*.txt`
  (through `scripts/build-guard.py`). It fails unless every observed outcome is a model
  outcome and, for an all-`seq_cst` test, an SC outcome.

Checked when `Sc.lean` is elaborated (`#guard`s run by the interpreter, not kernel `decide`; kernel-checked litmus proofs are phase 4):

| Fact | Result |
| --- | --- |
| model outcomes include every SC interleaving outcome | holds for all nine tests |
| `sb seq_cst`: `r0=r1=0` | RC11 forbids it, the model produces it (ORD-03 counterexample) |
| `2+2w seq_cst`: final `x=1,y=1` | RC11 forbids it, the model produces it |
| `iriw seq_cst`: `1010` (readers disagree on the write order) | RC11 forbids it, the model produces it |
| model outcome sets of `seq_cst` and of release/acquire | equal for `sb`, `2+2w`, `iriw`: no litmus proof can tell them apart |
| `sb release_acquire`, `sb mixed`, `2+2w release`, `iriw acquire`: the weak outcome | RC11 allows it, the model produces it |

The second fact is why C10 is open: the model is an over-approximation (sound for safety), but
the acceptance asks that SC and acq-rel differ.

Native observations (200 000 rounds each; the forbidden SC outcome is `00` for `sb`, `11` for
`2+2w`, `1010` for `iriw`):

| Test | aarch64-macos | aarch64-linux | x86_64-linux (Rosetta) |
| --- | --- | --- | --- |
| `sb relaxed` `00` | 72 588 | 15 701 | 10 |
| `sb release_acquire` `00` | 0 | 0 | 12 |
| `sb seq_cst` `00` | 0 | 0 | 0 |
| `sb mixed` (SC thread + RA thread) `00` | 0 | 0 | 13 |
| `2+2w relaxed` `11` | **26** | 0 | 0 |
| `2+2w release` / `seq_cst` `11` | 0 / 0 | 0 / 0 | 0 / 0 |
| `iriw acquire` / `seq_cst` `1010` | 0 / 0 | 0 / 0 | 0 / 0 |

Every observed outcome is a model outcome, and every `seq_cst` outcome is an SC outcome.
Reading the table:

* The hardware gives SC for `seq_cst` as required (LLVM: `ldar`/`stlr` on ARMv8, `xchg` on
  x86). aarch64's `stlr`/`ldar` are RCsc, stronger than C11 release/acquire, so release/acquire
  `sb` shows no `00` there although RC11 and the model allow it. An x86 `mov`/`mov` pair shows
  it. The hardware never exceeds the model.
* `sb mixed` on x86 shows `00`: one `seq_cst` thread does not order the other. The model
  and RC11 allow it. Any stronger rule must keep it (below).
* `2+2w relaxed` `11` is a *new* weak outcome observed on Apple silicon (not in T04). It is
  allowed by the model.
* `iriw` `0101` appears under `seq_cst` and is a sequentially consistent outcome (reader A
  read `x=0` then `y=1`, B read `y=0` then `x=1`: the order A.x, B.y, Wx, Wy, A.y, B.x explains
  it); only `1010` is the anomaly. The digits are easy to misread, so `Sc.lean` decides with the
  interleaving oracle, not by eye.

**Rosetta caveat.** The x86_64 column runs x86 machine code translated to arm64 by Rosetta. On
Apple silicon Rosetta uses the hardware TSO mode, so the observed orderings are x86-TSO
(`sb relaxed` `00` appears, `mp relaxed` `10` never does in T04's `litmus.zig` run under the same
container), but it is not x86 silicon: the translated code runs on arm64 cores, the rate of
store-buffering outcomes (10 per 200 000) is a property of that translation and of the core, not
of any x86 CPU, and the translator may order more strongly than x86 at places the tests do not
reach. The column shows that the TSO-visible shapes are within the model, and that `xchg`-based
`seq_cst` stores are respected by Rosetta; it is not evidence that real x86 silicon respects the
SC mapping. A run on a native x86_64 machine is the missing evidence (phase 0 below).

## Options

1. **Keep `seq_cst` as `acq_rel` and `unordered` rejected (today).** Sound (over-approximation),
   no work. Fails the acceptance, and blocks real std code (`Mutex` in Debug, `Io.Threaded`).
2. **SC as a global synchronizing clock.** An SC op acquires and releases one global vector
   clock. Easy, and gives SC for all-SC programs. Wrong: it adds happens-before edges between SC
   ops on different locations that RC11 does not have. Those edges hide real data races from the
   race check (T1 writes plain data then stores SC to `a`; T2 loads SC from an unrelated `b`,
   then reads the data plain: the global clock makes it race free, RC11 and the hardware do not).
   That removes outcomes the target permits and turns a race into a silent pass. Rejected.
3. **Scheduler order as the SC order, enforced by two floors (recommended).** The model is
   already an interleaving scheduler; the order in which SC operations execute *is* a candidate
   total SC order. Add (a) a message flag `Msg.sc` (written by an SC store or SC RMW) and the
   per-location `lastSc` (position of the newest `sc` message in modification order, derived,
   no new state), (b) a read floor: an SC read (SC `atomic_load`, the read of an SC RMW, an SC
   `cmpxchg` success or failure) reads at or after `lastSc`, (c) a write slot floor: an SC write
   goes after `lastSc` in modification order, so SC writes are modification-ordered in
   execution order. Nothing is added to the thread clocks, so no happens-before edge appears
   and the race check is unchanged. Reasoning for the litmus family: `sb` (the later of the two
   loads executes after both stores, so it reads 1), `iriw` (a reader's second load executes
   after the first writer it saw and after the write that preceded it in the execution order),
   and `2+2w` (the modification orders of both locations follow the execution order, so a
   cycle needs a cyclic execution order). Mixed programs keep RC11's weak outcomes: a non-SC op
   has no floor, so `sb mixed` `00` stays. This is the operational reading of RC11's `psc`
   restricted to SC accesses, as in the SC view of the Promising semantics (Lee et al.,
   PLDI 2020); the RC11 SC read condition (Lahav et al., PLDI 2017, where `scb` has `mo` and
   `fr` edges) is what (b) and (c) say when the SC order is the execution order. Completeness
   (the stronger model removes no RC11 outcome) is not obvious and must be shown, see below.
4. **Full RC11 axiomatic checker as the model.** Enumerate executions and check `psc`
   acyclicity. Exact, but the project's rules are operational (`FTriple`, `CTriple`, `fsym`
   walk a step function); a second semantics is a new framework. Rejected for the model; kept
   as the *test oracle* of option 3 (below).
5. **Promises plus SC** (the C12 long-term direction: Promising 2.x or IMM certification).
   Removes ORD-02 as well, but is the large effort C12 sized; option 3 is a step toward it and
   is not wasted.

## Recommendation

Option 3 for `seq_cst`, and an LLVM-faithful `unordered` for loads and stores in all modes, both
as changes to the one model (`ZigLean/Mem/Thread.lean`, `AtomicPtr.lean`, `Conc/AtomicWord.lean`)
and library lemmas about it. No new judgment, tactic or template.

### `seq_cst`

Model (library): `Msg.sc`, `ALoc.lastSc`, and the two floors above in `readOpts`/`writeSlots`
(they take the order). Each existing atomic op already passes its order. The unchanged parts:
`acq_rel` rule for clocks, `racePair` (atomic accesses never race), the messages and release
sequences.

Completeness evidence (before the model changes land, so a mistaken floor is caught): a small
executable RC11 oracle in the test directory (`psc`/`scb`, `hb`, `eco` over the enumerated
executions of a litmus family: `sb`, `iriw`, `2+2w`, `wrc`, `mp`, `r`, `s`, `corr`, and the mixed
variants, over relaxed/acquire/release/SC, 2 to 4 threads, up to 3 ops per thread), and a
checked comparison: the model's outcome set (with the floors) equals the oracle's for
every test. This is what "stronger rules never remove an outcome the model permits" means for a
checked family; it is exact for the family, not a proof for all programs. A proof for all
programs is the simulation lemma between the operational step relation and `psc` acyclicity,
which phase 3 sizes.

Fail-closed until then: unchanged. `seq_cst` stays accepted with `acq_rel` semantics and ORD-03
(a superset of RC11, so universal properties are sound). Any theorem whose proof needs the SC
order is not provable, which is the honest state; no rule may *assume* SC.

Logic. `fsym` needs no new judgment: an SC op is one of the existing `MemM` atomic steps, and the
new floors are hypotheses on the step lemmas (`readOpts_sc`: an SC read's options are positions
at or after `lastSc`; `writeSlots_sc`: an SC write's slots are after `lastSc`). A litmus proof
is a `WP`/`CTriple` over all schedules with an inductive invariant on `Mem` (the existing
rely-guarantee form of `Conc/Logic.lean`): for `sb` the invariant "the location's SC-written
value is in its `lastSc` suffix" plus the program-counter facts of the two threads gives "not
both loads returned 0". The new reusable resource is a pure assertion over the existing `apts`:
`apts_sc p S` meaning "the messages of `p` at or after `lastSc` have values in `S`", with the
rules: an SC load returns a value of `S`; an SC store of `v` leaves `S' = {v} ∪ (S written by
non-SC stores afterwards)` (stable under the rely: only a non-SC or later SC store extends it).
This is a library predicate and `@[fsym]` rules on `atomicLoadAt`/`atomicStoreAt` with an SC
order, in the style of `FTriple.atomicLoad`; the sequential rules (`choice 0`) are unchanged
because for one thread the newest message is the `lastSc` suffix.

### `unordered`

LLVM LangRef: `unordered` guarantees no tearing, no out-of-thin-air values, and that a read
returns a value some store wrote that is not hb-superseded; no coherence, no ordering, no
synchronization; it may be hoisted, merged, forwarded or dead-store-eliminated. Zig lowers to it
verbatim. The model:

* Load: any message at or after the hb floor (the newest message that happened before the
  reader); not bounded by the thread's own earlier reads and does not update them (this is
  `unorderedOpts`, already implemented). Admit it for every atomic pointee, in every allocator
  mode, not only under `--allocator-model translated`.
* Store (new): a message placed at any slot at or after the hb floor (so it may sit modification-
  order-before a message the thread itself read or wrote, which is the lost coherence), with no
  release clock, not recorded as the thread's own observation. The thread's later read still
  sees at least its own store (the store's clock is at or before the thread's clock, so the hb
  floor covers it). Dead-store elimination and merging are covered by the superset: the model
  lets every store be seen.
* RMW and `cmpxchg`: the compiler rejects `unordered`; nothing to model, and the translator
  keeps its existing rejection for an `unordered` RMW (it cannot occur in AIR).
* Races: an `unordered` access is atomic for the race check (`racePair`); against a plain access
  it races (`.illegal`), as in C++/LLVM.
* Liveness: no progress guarantee. LLVM may hoist an `unordered` load out of a loop, so a spin
  on an `unordered` load may never terminate; C13 must treat a wait on an `unordered` read as
  no progress evidence (a `monotonic` read is also not guaranteed to be eventually fresh by the
  standard; `unordered` is weaker still in practice).

Why this is a model change and not a per-fixture admission: the allocator-only admission today
exists because the proofs needed one load. `Thread.Mutex.DebugImpl` (0.14.1, 0.15.2), `lockStderr` and the
page-size cache need loads *and* stores; the same two rules cover them.

Logic: `FTriple.atomicLoadUnorderedEnc` exists for the sequential case. The store gets the
symmetric `FTriple.atomicStoreUnordered` (choice 0 in a sequential run: the newest slot) and the
concurrent reading is again the invariant form: an `unordered` read returns a value of the
location's hb-suffix, expressed by the same `apts` abstraction; a value never read
for synchronization (the DebugImpl `locking_thread` check) is proved by the invariant "the cell
holds this thread's id or not-my-id" which needs no ordering.

### Premises

* **ORD-03** is retired when phase 2 lands (the statement becomes "the SC order is the
  execution order of SC operations"), replaced by an environment premise **ORD-07** (SC
  mapping): "the compiled code's SC accesses are totally ordered consistently with the model's
  floors on the target", whose qualification is C12's `memory_model` record plus the new
  `sc-order` observations as evidence rows (per target: x86_64-linux, aarch64-macos,
  aarch64-linux) and the RC11-to-x86/ARMv8 mapping theorems (Lahav et al. 2017, Podkopaev et al.
  2019).
* **ORD-01**'s `unordered` sentence is generalized: the `unordered` load/store rules above
  (environment, LLVM LangRef semantics), no allocator-mode condition. If a separate ID is
  preferred, **ORD-08** (LLVM `unordered`).
* New IDs are assigned in `docs/premises.md` and `assurance/premises.json` when the model
  changes land, not in this PR (research PR: no premise table change).

## Acceptance evidence that closes the row

1. `Msg.sc`/`lastSc` floors in the model; `Sc.lean`-style tests turn from "model includes the SC-
   forbidden outcome" into "model excludes it" for `sb`, `2+2w`, `iriw` seq_cst, while
   `sb mixed`, `sb release_acquire`, `2+2w release`, `iriw acquire` keep the weak outcome.
2. Equality (checked by `#guard`, later `decide +kernel`) with the executable RC11 oracle over the litmus family.
3. Kernel-checked litmus proofs in the logic (not `#guard`): `sb_sc_not_both_zero` and
   `iriw_sc_agree` as `CTriple`/`WP` theorems over all schedules; a mutant (one `release`/
   `acquire` in place of `seq_cst`) fails to prove, with the model counterexample.
4. `unordered` store/load accepted in every allocator mode; `Thread.Mutex.DebugImpl`
   `locking_thread` (0.14.1, 0.15.2) and `Io.Threaded.lockStderr` translate and prove mutual exclusion of the
   lock itself (the `unordered` cell only checks).
5. Native: the three-target litmus table above regenerated by `scripts/` (a `sc-order` mode of
   `scripts/weak-ordering.py` or a sibling), plus one run on native x86_64 silicon; every
   observed outcome is a model outcome, every all-SC outcome an SC outcome; premises ORD-07/
   ORD-08 in `assurance/premises.json` with the evidence files.

## Risks and open points

* Completeness of option 3 for mixed programs is the main risk; the oracle (phase 1) and the
  mixed litmus tests are the guard, and the fallback is to keep ORD-03 for any shape the oracle
  disagrees on.
* LLVM may weaken or reorder around SC accesses beyond the C++ model (optimizations); that is
  already ORD-06's assumption.
* Fences would require a revised rule (RC11's SC fence terms, `psc_F`, differ from the SC access
  terms and the SC-access/SC-fence interaction is a known weak point of C11 and of RC11); not
  needed while Zig has no fence.
* The self-hosted backends other than x86_64 are not qualified.
* Rosetta is not x86 silicon (above).
