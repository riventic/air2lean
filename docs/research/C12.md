# C12 — Memory-model adequacy

Status: research; the premise is named, carried and checked
([ROADMAP](../../ROADMAP.md), [acceptance](../../remaining-acceptance.md#c12--memory-model-adequacy)).

## Question

Concurrency theorems are proved in the model: an interleaving scheduler whose race check makes
every data race between plain accesses `.illegal` (THR-01), and an approximation of RC11 for
atomics (ORD-01) with no load buffering (ORD-02) and `seq_cst` as `acq_rel` (ORD-03). A theorem
about the model transfers to the compiled program only if every behaviour of that program, after
LLVM's optimizer and lowering and on the target's hardware memory model, is one of the model's
outcomes. Which argument supports this, for which subset, and how does a claim show that it
rests on it? The acceptance asks that concurrency reports identify this premise and its
qualification evidence, and that it does not disappear behind a general claim of race freedom.

## Options

1. **A target/compiler correspondence argument for the supported subset.** For plain accesses:
   the model rejects every race, so a theorem is about race-free executions, and LLVM's C++11
   model gives those sequential consistency (DRF-SC). For atomics: the C11 mappings to x86-TSO
   and to ARMv8 that LLVM uses are proved sound for RC11 (Lahav et al., PLDI 2017) and through
   the intermediate model IMM (Podkopaev, Lahav, Vafeiadis, POPL 2019); ORD-01 admits every
   RC11 outcome. What is not covered: LLVM's optimizations of atomics (assumed C++11-sound), and
   load buffering, which RC11 forbids by axiom and ARMv8 permits (ORD-02). Cost: a written
   argument per target plus litmus evidence; no new proof.
2. **Verified usage restrictions.** The translator rejects programs outside a fragment where the
   model is exact: for example a DRF fragment with no relaxed atomics, or the no-load-buffering
   shape check already in `Check.lean` (`checkLoadBuffering`), made complete. Sound for what it
   accepts, but it rejects real std code (relaxed counters in `Io.Threaded`, weak-CAS loops),
   which works against full-language support.
3. **Expand the model.** Add promises (Kang et al., POPL 2017) or IMM-style
   load-buffering certification, so that ORD-02 disappears, and a global SC order, so that
   ORD-03 disappears. Then the remaining premise is only the compilation-correctness results
   above. This is the long-term end state, and it is a large proof-engineering effort: every
   concurrency rule (`ZigLean/Conc/*`) would be re-proved over a larger outcome set.

## Recommendation

Option 1 now, made visible and checked; option 3 as the long-term direction, scheduled after
C10 (SC order and unordered operations).

- The premise is **ORD-06** ([premises.md](../premises.md#ord-06)), kind *trusted*. THR-01 and
  ORD-01 imply it, so every theorem that reaches the scheduler or the atomics model carries it:
  1647 of the 3094 indexed theorems at this commit.
- The **qualification record** is the `memory_model` block of
  [assurance/premises.json](../../assurance/premises.json): per target that accepts atomics and
  threads (x86_64-linux, aarch64-macos, aarch64-linux) the hardware model, the argument and the
  evidence files (weak-CAS native gate, architecture-audit litmus programs, aarch64 litmus and
  synchronization probes, the atomics differential test); and the targets that reject
  concurrency (wasm32, s390x), so no theorem about them needs the premise.
- **Checks.** `scripts/premises.py check` fails when an indexed theorem whose premises contain
  THR-01 or ORD-01 lacks ORD-06, when a report in the premises catalogue rests on a concurrency
  premise without listing ORD-06 itself, and when an evidence file of the record is missing.
  `scripts/premises.py compiled` applies the same theorem check to the kernel dependency graph.
  `scripts/claims.py` lists ORD-06 in the `premises` of every claim whose closure reaches a
  concurrency runtime module (from the audit's new per-theorem `runtime_modules`), and rejects a
  goal whose audit lacks that closure or reaches an unmapped runtime module.

This supports the whole language: the premise attaches by the runtime modules a proof reaches,
not by program shape, so every current and future concurrent client carries it without
per-client work. The option 2 restriction stays as it is (the load-buffering shape check
narrows ORD-02), but it is not extended into a fragment that rejects std code.

## Why not option 2 alone

The std synchronization code that the project translates (`Io.Mutex`, `Io.RwLock`,
`Thread.Mutex.FutexImpl`, weak-CAS stacks) uses relaxed and acquire-release atomics that a
DRF-only fragment rejects. Full-language support needs the relaxed fragment, so the premise has
to be argued, not designed away.

Scope of the checks: `scripts/claims.py` derives ORD-06 from the runtime modules a closure
reaches. Every concurrency token rule of `assurance/premises.json` names a runtime declaration
(`atomicLoad`, `spawnC`, `Os.futexWait`, ...), so a closure that matches one also reaches its
mapped module; `scripts/premises.py compiled` applies the token rules as well. The checks do not
yet bind a theorem's profile target to a qualified `memory_model` target: today that binding is
the translator's rejection of atomics and threads on wasm32 and s390x.

## Next steps

1. C10: a global SC order (removes ORD-03) and `unordered` semantics.
2. Promises or IMM certification in `ZigLean/Mem/Thread.lean` (removes ORD-02 and the
   per-target load-buffering caveat on aarch64).
3. Native litmus runs for aarch64-linux load buffering on more than one implementation, recorded
   per target in the `memory_model` evidence.
4. Bind each concurrency theorem's generated-module profile target to a qualified
   `memory_model.targets` entry in `scripts/premises.py`, so the record fails closed by itself.
5. Before wasm32 accepts threads: a wasm32 entry (the WebAssembly threads proposal's memory model
   is a JavaScript-style SC-DRF model with its own mapping argument).
