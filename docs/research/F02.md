# F02 — Transcendental specifications

Status: research, with two recorded native probes
([ROADMAP](../../ROADMAP.md), [acceptance](../../remaining-acceptance.md#f02--transcendental-specifications)).

## Question

`@sin @cos @tan @exp @exp2 @log @log2 @log10` are translated to `Zig.Float.libm op x`, an
`opaque` function (premise MTH-02, `ZigLean/Float/Libm.lean`). A theorem can say nothing about the
value, not even `@exp x > 0` or `@sin x ∈ [-1, 1]`. The acceptance asks for domain,
classification, monotonicity and error-bound contracts that are either verified implementation
models or explicit target-qualified assumptions, and for a real numeric client that proves a
useful property from one. A test-only FFI implementation (`tests/diff/libm`) must never be
treated as a kernel theorem.

## What Zig does (sources: pinned CAS, 0.14.1 / 0.15.2 / 0.16.0 / 0.17.0)

- **Lowering.** The LLVM backend (`src/codegen/llvm/FuncGen.zig`, `airUnaryOp`) emits the LLVM
  intrinsic (`llvm.sin.f64`, ...) when `intrinsicsAllowed(.libc, ty, target)`. LLVM then either
  folds it or emits a libcall (`sin`, `sinf`, `sinl`). For `f16`, `f80`, `f128` (no libc name), the
  backend calls the compiler_rt names `__sinh`, `__sinx`, `sinq`, and so on (0.17.0
  `Air/Legalize.zig` `.__sinh`; 0.16.0 renamed sin/cos/tan's `__sinh`/`__sinx`).
  Comptime evaluation (`Value.sinScalar`) runs the compiler's own host `@sin`, so a comptime
  and a runtime result can differ.
- **Who provides the symbol.** compiler_rt exports `sin sinf sinl __sinh __sinx sinq` (and the
  same for the other seven ops) with weak linkage (`compiler_rt.symbol`). So:
  - no libc (freestanding, wasm32-freestanding, Linux without `-lc`): compiler_rt's Zig code
    (a port of musl's `sin.c`, `exp.c`, FreeBSD's `k_*`, plus Tang's table method for f128
    `exp`/`exp2`, `log_f128.zig`);
  - macOS: libSystem's libm for `f32`/`f64` (checked: `nm -mu` of a 0.15.2 binary lists `_sin`,
    `_sinf`, `_exp`, `_expf`, `_exp2`, `_log`, `_logf` "from libSystem"). `f16`, `f80` and `f128` are
    still compiler_rt;
  - Linux with glibc: the dynamic glibc libm. Linux with musl (Zig bundles it): musl's C
    (0.17.0 `lib/c/math.zig` ports only part of libm to Zig, not these eight);
  - Windows/MinGW: the CRT's libm.
- **compiler_rt is not the exact function.** `f16` goes through `f32`. In 0.14.1 and 0.15.2 the
  `f80` and `f128` versions of all eight ops are `f64` code behind a `@floatCast`
  (`sinq`, `expq`, ... call the `f64` function), so extended results are `f64`-accurate and
  overflow or underflow at `f64`'s range. 0.16.0 has real `f80`/`f128` `sin`/`cos`/`tan` code
  (musl `ld80`/`ld128` ports) and `exp_f128.zig`/`log_f128.zig` files; 0.17.0 keeps them (not
  every op/version pair was audited; phase 1 must tabulate it from the sources). Probe `f128_via_f64.zig` (Zig 0.15.2, aarch64-macos):
  `@exp(@as(f128, 1000))` is `inf` (the true value, 1.97e434, is far below `f128`'s maximum),
  and `@log(1 + 2^-60) - 2^-60` is `-8.67e-19` where the exact value is `-2^-121`.
- **Accuracy.** compiler_rt's own comments: `log` worst case 0.530 ulp (f64) and 0.528 (f32),
  `log2` 0.594/0.546, `log10` 0.591/0.565; `exp.zig` records "off in the last bit in 64-bit,
  disagreeing with GCC". No function is documented correctly rounded, none is proved. Probe
  `libm_vs_compiler_rt.zig` (200 000 seeded draws per row, same binary, macOS libSystem vs
  compiler_rt): f64 `sin`, `exp`, `log`, `exp2` and f32 `sin`, `exp` agree bit for bit on every draw;
  f32 `log` differs on 1960 draws (about 1%) by one ulp. The T05 record shows the `@sin`
  difference of one ulp on other inputs. Two faithful implementations may differ, so no
  theorem can name "the" value without naming the implementation.

## Existing model

`Float.libm : LibmOp → Float fmt → Float fmt` is `opaque` with `@[implemented_by]` to the static
archive built from Zig's compiler_rt for the differential test. `Proofs/Floatops` mentions it only
inside op selectors. The assumption audit maps `libm` tokens to MTH-02. F01 labels
(`ieee | compiler-rt@versions | abstract-spec`) have no label for "assumed implementation
contract", F04's `Float.Allowed` covers NaN payload variation only.

## Options

1. **Keep opaque (status quo).** Sound, useless: no client can prove range facts.
2. **One global axiomatic spec** ("`@exp` is faithfully rounded for all targets"). Unsound for
   `f128` (the probe above), for older compiler_rt and for macOS vs Linux; and one global
   hypothesis is an unqualified assumption.
3. **Implementation-qualified contract premises.** A Lean `Prop` (structure) `LibmContract impl op fmt`
   over `Float.libm`; each field is a checkable statement; a profile selects the `impl`; a
   theorem takes the contract as a hypothesis, and the premise registry names it. Validation is
   evidence outside the kernel (exhaustive f32 and sampled f64 runs against a high-precision
   reference, the existing `tests/diff/libm`), recorded per implementation.
4. **Verified models.** Translate the real compiler_rt Zig through the pipeline so the `libm`
   function is *defined* by generated code, then prove properties by `fsym`. Exact `Float`
   semantics make special-value, classification and range-reduction facts provable. A tight
   ulp bound for a polynomial/table algorithm needs real analysis (rational enclosures of
   the function, polynomial remainder bounds, table correctness): large, per function and per
   format. The f32 domain is finite but 2^32 cases are out of reach for kernel `decide`; the
   project forbids trusting `native_decide`-style evaluation for theorems.
5. **Interval specs only** (`libm x ∈ [lo(x), hi(x)]` from certified rational enclosures). This is the
   shape of the error-bound field in option 3 and of the proofs in option 4; it is a
   representation of the bound, not a competing option.

## Recommendation

Option 3 now, growing into option 4 per function where the bounds are proved, with one
contract shape for both so a client never changes.

1. **Library, no new judgment.** `ZigLean/Float/Libm.lean` gains a `structure LibmContract (op) (fmt)`
   with `Prop` fields only, on top of the unchanged opaque `Float.libm`:
   - *special values* (decidable, exact): the IEEE/C Annex F table (`exp ±0 = 1`, `exp -∞ = +0`,
     `log 1 = +0`, `log ±0 = -∞`, `log x<0 = NaN`, `sin ±0 = ±0`, `sin ±∞ = NaN`, ...). Every
     compiler_rt and libm in the survey meets these;
   - *classification*: NaN in gives NaN out; domain errors give NaN; the result is finite for finite
     arguments within the documented range (overflow bounds as rational constants);
   - *error bound*: stated on `Float.toRat?` against a rational enclosure of the true function:
     for finite `x` with `lo ≤ f(x) ≤ hi` and the result in the normal range, the result is
     within `k` ulp of the enclosure. The enclosure lemmas (`exp`, `log`, `sin` bracketed by Taylor
     remainders on `Rat`) are proved once in the library; `k` is a per-implementation constant.
     `k = 1` is "faithful"; the correctly rounded case is `k = 1/2`;
   - *shape* (optional, separate fields, each its own premise strength): monotonicity of `exp`,
     `exp2`, `log*` (a faithful implementation need not be monotone; `Float.Allowed`-style
     "result within the set" does not give it), and `sin`/`cos` range `[-1, 1]`.
2. **Selection by the F01 profile.** The generated header already records the target, version,
   libc admission (`--assume-no-libc`) and float semantics. Add a derived field `libm_impl`
   in the profile, from the table above: `compiler-rt@<version>` (no libc, wasm32, `f16`/`f80`/`f128`
   everywhere), `libsystem` (macOS f32/f64), `glibc`, `musl`. A theorem that uses a contract states the
   `impl`; the F01 label gets a fourth class `libm-contract@<impl>` so audits show it.
   Fail closed: until a profile/format has a registered contract, the contract hypothesis cannot be
   discharged for it (for example `f128` before 0.17.0 has only the special-value and
   classification fields, not an error bound a client would assume to be accurate).
3. **Premises.** `MTH-02` stays: opaque, no contract. Add `MTH-06` "compiler_rt transcendental
   contract" (per Zig version and format; `k` and the shape fields; validated by the differential
   test and an exhaustive `f32` sweep; the evidence file is the receipt) and `MTH-07` "platform libm
   contract" (per `libsystem`/`glibc`/`musl`/MinGW; vendor behaviour, version unpinned, so only the
   special-value, classification and `k ≤ 1` fields, and a recorded probe, never a binary claim).
   Each registered in `docs/premises.md` and `assurance/premises.json`, listed by every claim that uses one.
4. **Option 4 as the long-term replacement for MTH-06.** compiler_rt is Zig source, so it can be
   translated. The order is by yield: (a) special values and classification (provable
   by `fsym` on the generated code; removes those fields from the premise); (b) range reduction
   and `sin`/`cos` `[-1, 1]`; (c) full ulp bounds via the enclosure lemmas, f32 first. Each
   proved field lowers the premise; the contract structure stays.
5. **Test FFI stays test-only.** `implemented_by` linkage supplies `#eval` behaviour; no theorem may
   depend on its value. The audit already blocks it (MTH-02 closure pattern); keep the pattern.

Why not Option 2: it is the shortcut that breaks when the target changes (f128, macOS, glibc).
Why not Option 4 first: it delays every client by the largest proof effort in the project's float
library, while a premise with evidence unblocks clients now and is lowered field by field.

## Acceptance evidence that closes the row

- `LibmContract` and the enclosure lemmas for `exp`/`log` (at least) in `ZigLean/Float`, with
  the premise IDs and audit label.
- A real client, translated from Zig, proved from the contract. Recommended: a numerically stable
  softmax or log-sum-exp (`exp(x - max)` is in `(0, 1]` and finite; the sum is finite, positive;
  every output is in `[0, 1]`). It needs only `exp` special values, `exp 0 = 1`, monotonicity
  and the `k`-ulp bound; the proof cannot be done from the opaque.
- A negative test: a mutant that assumes the `compiler-rt` contract for `f128 @exp` on 0.15.2 is
  rejected (the probe `f128_via_f64.zig` gives the counterexample: `exp(1000) = inf`).
- The profile-to-implementation table checked in CI against the pinned compiler sources (the
  weak-symbol facts above) and by a macOS/Linux probe like `libm_vs_compiler_rt.zig`.

## Premises and decisions

New: MTH-06, MTH-07 (names proposed). Decisions for the maintainer: (1) accept the fourth F01
label `libm-contract@<impl>`; (2) whether monotonicity is a separate premise strength or
excluded until proved; (3) whether `libsystem`/`glibc` contracts are admitted at all (they
cannot be proved from Zig source, so they rest on vendor behaviour) or the translation rejects
libc-linked transcendentals until phase 4 covers them.
